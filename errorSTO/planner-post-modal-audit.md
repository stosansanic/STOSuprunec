# Аудит модалки цехів і постів `postPostModal`

Дата: 21.10.2026.

## Виявлені проблеми

1. Без вибраного `post_id` редагування або видалення могло застосуватися до
   першого поста цеху. Введений текст не був надійним ідентифікатором запису.
2. Перейменування цеху втрачало його ID; вибір клавіатурою і мишею змінював
   різні частини стану. Після очищення тексту могли залишатися попередні ID.
3. Створення цеху, поста й призначення слюсаря виконувалось послідовними
   HTTP-запитами. Збій посередині міг залишити лише частину зв'язки.
4. Клієнт обчислював `max(id) + 1`; одночасні користувачі могли отримати той
   самий ID. Пошук точного імені через `ilike` трактував `%` і `_` як шаблони.
5. Видалення не перевіряло посилання з працівників і бронювань. Базова схема
   не містить зовнішніх ключів, які автоматично захищали б ці зв'язки.
6. Під час збереження можна було закрити форму або змінити режим; запізніла
   відповідь могла вплинути на вже інше відкриття модалки.
7. При відкритті читалися всі назви цехів і постів без пагінації. Після
   додавання рядка планувальник повторно читав бронювання видимого періоду.
8. Редагування довідника не оновлювало заголовки вже відкритого календаря.

## Реалізована поведінка

- Режим довідника: додавання цеху або поста, редагування вибраного запису
  лише за ID й початковими значеннями, видалення лише невикористаного запису.
- Режим створення рядка: атомарно знайти або створити цех, пост, працівника
  та зберегти призначення. Повтор того самого призначення не створює дубль.
- Неоднозначні однакові ПІБ потребують вибору конкретного працівника.
- Пост із працівником або історією бронювань не видаляється. Цех із постами
  також захищений. Перейменування не змінює ID або історичні бронювання.
- Збереження блокує поля, режими й закриття до завершення операції.
- Сервер використовує `SECURITY INVOKER` і чинні RLS-політики. Нових правил
  доступу або автоматичного перенесення історії не додається.

## Запити й трафік

- Відкриття форми саме по собі не робить запитів. Підказки завантажуються
  при взаємодії з полем, по 30 записів; API обмежує порцію максимум 50.
  Підказки повертають тільки ID, назву та необхідний ID цеху для поста.
  Зарплатна історія й увесь JSON працівника не надсилаються.
- Сторінки підказок кешуються в межах відкритої форми; повторні однакові
  запити об'єднуються. Наступна сторінка потрібна лише при прокрутці користувача.
  Пошук має затримку 250 мс. Повний отриманий результат може звужуватися
  локально; неповний список не використовується як повний довідник.
  Кеш обмежено 96 сторінками й очищується при закритті або зміні користувача.
- Незмінене редагування не виконує запису. Операція збереження — один RPC
  із короткою відповіддю. Наявний журнал фактичної операції рахується окремо.
- Перейменування оновлює відповідні підписи локально, без читання бронювань.
- Додавання рядка зберігає наявні блоки календаря. Якщо потрібна історія
  доданого працівника, читається лише він за поточний видимий період.

## Встановлення

Для чинного проєкту: весь
`supabase/setup/traffic-optimization/planner-post-modal-repair.sql` у SQL Editor,
після цього опублікувати frontend. SQL не вставляти в редактор Edge Functions.
Для нових проєктів пакет уже включено до
`D:/Alim/Proekt/Основа проектів/8 зменьшує вихідний трафік.sql`.

Міграція додає індекси для постів цеху та історичних посилань на пост.
Якщо імпорт раніше залишив serial-лічильник слюсарів позаду фактичного
найбільшого ID, під час встановлення вирівнюється лише цей лічильник.
Рядки працівників та їхня історія не змінюються.

## Перевірки та межі перевірки

Спільний фінальний прогін: **86/86 перевірок успішні**:

- 22 SQL-сценарії: транзакції, конфлікти, повтор операції, однакові назви,
  явні ID, RLS, історичні посилання, компактні сторінки, serial-лічильник.
- 33 перевірки модалки: вибір мишею/клавіатурою, режими, незмінена форма,
  повторне натискання, кеш, пагінація, запізнілі відповіді, зміна користувача.
- 22 перевірки інтеграції календаря: локальні підписи, збереження DOM-блоків
  та їхніх обробників, короткі квитанції, читання лише доданого працівника.
- 9 суміжних перевірок читання бронювань, зайнятості та Realtime.

`npm run build:vercel` та перевірка TypeScript успішні. Залишилися попередні
попередження Vite щодо великого головного JS-файлу та змішаного імпорту модуля.
Перевірено відповідність вихідної міграції, датованої копії, repair-пакета
та єдиного блоку у файлі №8. Форматування змінених TypeScript-файлів перевірено.

SQL виконувався на синтетичних даних у PGlite. Перевірка черги одночасних
викликів не замінює навантажувальну перевірку окремих PostgreSQL-сесій.
Серверні блокування захищають транзакцію; базова схема надалі не має FK
для цих старих зв'язків, тому сторонні старі прямі записи після транзакції
не отримують нових гарантій цілісності. Чинні правила доступу не розширювалися.

Локальні зміни довідника відображаються відразу. Нові Realtime-підписки
на цехи/пости не додаються; інша вже відкрита вкладка отримує оновлені
довідники при повторному завантаженні. Чинні Realtime-оновлення бронювань
збережено. Робоча база Supabase не змінювалася; фактичні мегабайти
production-трафіку не вимірювалися.
