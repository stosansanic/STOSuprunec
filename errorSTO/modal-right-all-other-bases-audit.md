# Аудит `modal-content-all_other_bases` та `modal-right-all_other_bases`

Дата: 21.10.2026. Обсяг: додавання, редагування, видалення та підказки довідників; сумісність спільного запису зі складським Excel-вікном. Повторний аудит охоплює всю зовнішню модалку: вкладки «Склад», «Робота», «Співробітники», «Контрагент», «Джерело», перемикання режимів, відкриття/закриття та запізнілі відповіді.

## Виявлені причини нестабільної роботи та виправлення

| Проблема | Виправлення |
| --- | --- |
| ID і стан магазину/деталі могли залишатися від попередньої форми та впливати на операцію іншого розділу. | Скидання стану при зміні розділу й закритті; диспетчеризація за поточним розділом; операція редагування/видалення потребує вибраного ID і початкових даних. |
| Повторні натискання й зміна форми під час перевірки пароля створювали ризик запису іншої версії форми. | Одне активне підтвердження, блокування форми на час операції та перевірка користувача/розділу/значень до й після перевірки пароля. |
| Після помилки форма могла скидатися або показувати успіх без фактичної зміни рядка. | Помилка збереження залишається видимою; чернетка не очищається; RPC і прямі записи перевіряють підтвердження конкретного ID. Нуль змінених рядків — помилка, а не успіх. |
| Профіль наступного працівника міг успадковувати порожні поля попереднього; незмінені значення або значення за замовчуванням могли повторно записуватися. | Повне очищення полів перед вибором працівника, початковий знімок для порівняння, передавання лише змін. Збережений пароль не підставляється у видиме поле. |
| Редагування реквізитів контрагента могло зачіпати лічильник накладних; стан одержувача відображався неточно для нуля. | Передаються лише змінені поля. Нуль — допустимий лічильник. Паралельні зміни інших полів зберігаються. |
| Відсутні у звичайній складській формі поля могли обнулювати прив'язку до акта, статус, примітку, використану кількість або ціну клієнта. | До запису входять тільки наявні елементи форми. Початкові значення приходять з однією вибраною позицією. |
| Історична одиниця виміру або неактивний склад могли зникати з `<select>`. | Поточне збережене значення додається до варіантів перед заповненням форми. |
| Перейменування магазину могло перезаписувати весь JSON разом з історією. | Атомарне редагування тільки `Name`, зі збереженням інших полів і перевіркою попереднього значення. |
| Старі назви робіт/деталей іноді зберігаються як JSON-об'єкт або JSON-рядок, а не звичайний текст. | Назва витягується за тим самим правилом, що й у складському довіднику; перейменування зберігає формат і додаткові поля, включно з паралельно зміненими. |
| Магазин і назва деталі без каталожного номера оброблялися незалежно. | Один атомарний `traffic_directory_reference_batch`: помилка другої операції скасовує першу. |
| Видалення могло повідомляти успіх після конфлікту або зачіпати використаний складський рядок. | Перевірка початкових значень, використаної кількості та акта; коротке підтвердження фактичного видалення. Для сторінки складу додано `kilkist_off` без додаткового запиту на кожне видалення. |
| Помилка пакетного додавання могла залишати тимчасові поля та режим CRUD для наступної операції. | Відновлення полів і режиму в `finally`; невдалий рядок зберігається для виправлення, інші рядки обробляються далі. |
| Склад міг зберегтися, а пов'язаний акт — ні; повторна спроба вважала рядок завершеним. | Окремо зберігається потреба синхронізувати акт. Повтор завершує її без повторного INSERT/UPDATE уже збереженої складської позиції. |
| Щойно доданий рядок не мав початкових даних для наступного редагування/видалення без перезавантаження. | Підтверджений новий INSERT залишає локальний знімок відправлених значень. При повторному використанні наявної накладної такий знімок не вигадується: поточні дані потрібно перечитати. |
| Після часткового успіху пакета вже видалений рядок повторно надсилався на DELETE й блокував завершення. | Підтверджені видалення/пропуски не повторюються; невдалі операції залишаються доступними для повторної спроби. |

## Повторна перевірка всієї модалки

- Режим «Додати / Редагувати / Видалити» має один спільний стан. Відображений режим збігається з виконуваною дією. Заблоковані поля й приховані кнопки профілю не переходять на інші вкладки.
- На час ініціалізації розділу збереження блокується. Повторний клік уже готової вкладки зберігає введені дані та не повторює авторизацію/ініціалізацію.
- Відповідь попереднього вибору, прихованої форми або іншого користувача не заповнює поточну форму. Старі пункти випадаючого списку не залишають активних обробників; Escape і клік поза списком скасовують відкладене відкриття.
- Власний профіль завантажується одразу за ID. Однакові ПІБ не змінюють визначення власника. Пізня відповідь запису чи видалення не скидає інший уже вибраний профіль/контрагента.
- Якщо початкове завантаження власного профілю завершилося помилкою, вкладка не позначається готовою. Повторний клік дозволяє повторити завантаження; помилка не маскується порожньою формою.
- Вибір складу, змінений користувачем під час завантаження варіантів, зберігається. Редагування власного пароля не перевіряє незмінювані застарілі фінансові поля.
- Після конфлікту запису кеш довідника скидається. Наступний явний вибір читає актуальні дані; автоматичного повторного запису немає.
- Магазини завантажуються лише при відкритті підказки, порціями по 50. Імена запчастистів — при першому відкритті, потім із кешу. Введений текст назви сам по собі не присвоює ID для редагування/видалення.
- Повний експорт робіт лишається явною дією з порціями по 1000. Закриття модалки або зміна користувача припиняє читання наступних порцій.

## Зменшення запитів і трафіку

- Для підказок працівників завантажуються ID, ім'я та роль; зарплатна історія не потрібна й не передається. Дані редагування одного профілю запитуються після вибору.
- Для магазинів — ID і назва; для робіт/деталей — ID і назва. Підказки робіт починаються з трьох символів.
- Сторінка довідника містить не більше 50 записів. Наступна сторінка приходить під час прокрутки.
- Однакові одночасні читання об'єднуються. Повторні відкриття підказки в межах модалки використовують кеш, а не новий запит через короткий таймер.
- Якщо попередній результат повний, подальше звуження пошуку фільтрується локально. Якщо результат неповний, новий пошук виконується на сервері, щоб не пропустити збіги.
- Кеш обмежений за розміром; очищається при закритті модалки, зміні користувача, зміні даних або відновленні мережі. Відповідь старої форми не потрапляє до нової.
- Незмінені дані не викликають запису. Проста незмінена форма також не викликає перевірки пароля. Перевірка пароля та журнал змін для реальної операції залишаються.
- Редагування надсилає змінені поля й відповідні попередні значення. Відповідь містить коротке підтвердження, а не весь масив історії.
- Вибрана складська позиція оновлюється/видаляється з уже отриманим початковим знімком; додаткове читання перед записом не потрібне.
- Пакетний імпорт повторно використовує вже визначені назви магазинів і деталей.
- SQL формує JSON відповіді після відбору поточної сторінки: додаткові поля профілю не витягуються для всіх збігів до пагінації. Загальна кількість збігів залишається правильною; мережевий контракт не змінений.

### Типові операції

Це кількість цільових запитів за контрактом коду; авторизація та наявний аудит реальної зміни рахуються окремо.

| Дія | Запити даних |
| --- | --- |
| Повторне відкриття вже завантаженої підказки | 0 |
| Звуження повністю завантаженого результату | 0 |
| Нова сторінка підказок | 1 короткий запит |
| Збереження незміненої форми | 0 запитів запису |
| Зміна одного поля вибраної складської позиції без нових назв | 1 UPDATE з коротким підтвердженням |
| Видалення дозволеної складської позиції з наявним знімком | 1 DELETE з перевіркою попередніх значень |
| Зміна магазину та назви деталі без каталогу | 1 атомарний RPC |

## Обмеження видалення

Профіль адміністратора №1, непорожня історія працівника/магазину, залишки в JSON магазину та використана/прив'язана до акта складська позиція не видаляються цією формою. Це запобігає втраті існуючих даних. Поточні RLS-політики бази залишаються чинними. При конфлікті потрібно повторно вибрати запис, а потім внести потрібну зміну.

## Встановлення

Для чинного проєкту з попереднім пакетом №8 виконати весь файл `supabase/setup/traffic-optimization/directory-modal-repair.sql` у **Supabase → SQL Editor**, потім опублікувати frontend на Vercel і перезавантажити сторінку.

Поточний repair включає попередні виправлення правої частини та повний актуальний SQL для зовнішньої модалки. Якщо попередню версію repair не встановлювали, достатньо виконати поточний файл один раз. Перевірено встановлення з попередніми базовими функціями без обох нових міграцій 21.10, а також повторне встановлення.

Для нових проєктів обидві міграції включено до `D:/Alim/Proekt/Основа проектів/8 зменьшує вихідний трафік.sql`. Окремі файли №8.x не створювалися. Датовані копії лежать у `supabase/migrations-by-date/10.21.26`.

## Межі перевірки

Пройдено 157 цільових автоматичних перевірок: 133 перевірки TypeScript-сценаріїв і 24 SQL-перевірки. Окремо звірено SQL-блок у файлі №8 із repair-пакетом, порядок визначень, датовані копії та фінальні межі транзакції.

`npm run build:vercel` завершився успішно разом із перевіркою TypeScript. Vite повідомляє про великий основний JS-файл і спільний статичний/динамічний імпорт модуля збереження акта; ці попередження не блокують збірку, перебудова всього frontend на частини не входила до цього аудиту.

Перевіряються локальні сценарії форми та SQL на синтетичних даних у PostgreSQL-сумісному PGlite: конфлікти, RLS, дублікати, атомарність, збереження історії, кешування, повторні натискання й імпорт. Це не вимірювання production-трафіку. Міграції у робочій Supabase та публікація на Vercel у межах цього аудиту не виконувалися.
