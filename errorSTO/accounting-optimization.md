# Оптимізація бухгалтерії — 12.10.2026

## Стан і встановлення

Зміни внесені локально. Supabase і Vercel цією роботою не оновлювалися. Нових таблиць і видалення історії немає.

1. На проєкті мають бути попередній пакет функцій читання бухгалтерії та `20261011080000_payroll_fragments.sql`.
2. У **Supabase → SQL Editor** виконайте повністю [20261012122102_accounting_traffic_optimization.sql](../supabase/migrations/20261012122102_accounting_traffic_optimization.sql). Це SQL, його не потрібно вставляти в Edge Functions.
3. Після успішного встановлення SQL опублікуйте оновлений frontend на Vercel. Окремої Edge Function для цих змін немає.

Копія для перегляду за датою: `supabase/migrations-by-date/10.12.26/`. Двічі виконувати оригінал і копію не потрібно. 12.10.2026 міграцію також додано до `D:/Alim/Proekt/Основа проектів/8 зменьшує вихідний трафік.sql` після попередніх залежностей, усередині спільної транзакції. Для нових проєктів, що встановлюють оновлений файл №8, окреме виконання цієї міграції не потрібне. Попередню версію №8 збережено у `8 зменьшує вихідний трафік.sql.before-accounting-20261012-161258-960.bak`.

## Межі кешування і збереження

- Кеш живе в пам'яті сторінки; зміна користувача, відповідних даних або явне оновлення робить його неактуальним. Дані звітів не записуються в localStorage.
- Зарплата та магазинні звіти з пагінацією фільтруються локально лише коли завантажено повний результат. Однієї видимої сторінки недостатньо для точних загальних сум.
- При оплаті звіти без фільтра оплати оновлюються локально. Якщо дія змінює склад вибірки («оплачені», «неоплачені», пошук за датою розрахунку), перечитується потрібна сторінка з підсумками.
- Масова виплата зарплати та магазинний розрахунок спочатку отримують усі відповідні сторінки. Це необхідно для оплати всіх вибраних рядків і перевірки їх початкового стану.
- Пакет записів атомарний у межах одного RPC. Успішно записані попередні пакети не відкочуються при помилці наступного; незбережені зміни відновлюються з останнього підтвердженого стану.
- Перевірки конкурентного редагування зарплати, заморожених актів і незавершеного нарахування залишаються у серверній функції `write_payroll_fragments`. Магазинний розрахунок перевіряє очікувану оплату та відбиток історії акта.
- «Лише змінені поля» стосується запиту й логіки оновлення. PostgreSQL усе одно може фізично переписати версію рядка/JSONB; це не означає пересилання всього JSON через інтернет.
- Міграція використовує чинні права і RLS через `SECURITY INVOKER`; політики доступу вона не розширює.

## Перевірка та обмеження

Додатково підготовлено [виправлення тайм-ауту звіту зарплати](payroll-timeout.md): міграція `20261012131746_traffic_payroll_report_timeout.sql`. На чинному проєкті вона виконується після попереднього оновлення бухгалтерії; в актуальний файл №8 вже включена.

Виконана компіляційна перевірка `npm run check` (`tsc -b`), без помилок. Проведено перегляд зв'язків читання, запису, кешу і SQL. Автоматичні тести, браузерні сценарії та виконання SQL на реальній базі в цьому етапі не запускалися.

Після встановлення потрібно перевірити пошук за датами, звуження/розширення періоду, одиничні та масові оплати, перемикання фільтрів оплати, журнал і приховану вкладку аналітики під робочими ролями. Це ще не виконане production-приймання.

Конкретний відсоток економії не виміряний. Порівнювати Supabase Egress і кількість запитів потрібно після розгортання на однакових робочих діях і за однаковий період.

Наступна зміна: [ліниві списки бухгалтерії](accounting-lazy-rows.md). Кнопки попередньої/наступної сторінки замінені прокруткою; у зарплаті/деталях/журналі використовуються серверні порції, у складі/прибутку — кеш періоду. Для зарплати й журналу потрібна міграція `20261012133426_traffic_accounting_lazy_rows.sql` перед публікацією frontend.
