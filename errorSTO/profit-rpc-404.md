# «Прибуток»: 404 для traffic_profit_acts — 13.10.2026

## Повторна помилка після встановлення — уточнення

Користувач підтвердив запуск міграції, але 404 лишився. Знайдено помилку
сумісності: початкова функція порівнювала `acts.rosraxovano` з параметрами text,
а базовий SQL-шаблон визначає це поле як timestamp. PostgreSQL перевіряє
оператори всіх гілок CASE; тому помилка можлива навіть у режимі «Відкриття».
Код 42883 також повертає HTTP 404. Попередній обробник помилково показував
для нього повідомлення про невстановлену зовнішню функцію.

Міграція `20261013120709_traffic_profit_date_compatibility.sql` вибирає поле
за режимом, отримує його тип із pg_attribute та приводить параметри до цього
типу. Типи обмежені timestamp/timestamptz/date/text/varchar; назва поля
вибирається з трьох констант і екранується через format %I, значення передаються
через EXECUTE USING. Колонки не приводяться до тексту, RLS і сторінки 200+1
збережені. Немає змін фінансових записів або нових таблиць.

у SQL Editor. Для нового точного повідомлення помилки потрібна публікація
фронтенду; для самого виправлення SQL повторна публікація не потрібна.

Фактичний JSON помилки та схема робочого проєкту досі недоступні. Помилку
сумісності встановлено за локальними SQL-файлами; її наявність саме у робочій

## Що встановлено

Користувач підтвердив адресу помилки: `/rest/v1/rpc/traffic_profit_acts`.
Фронтенд передає `p_mode`, `p_from`, `p_to`, `p_offset`; їхні назви відповідають
визначенню в `20261011010000_traffic_profit_acts.sql`. Після помилки читання актів
завантаження звіту припиняється, тому прибуток не відображається.

404 разом із кодом PostgREST `PGRST202` означає відсутню функцію або застарілу
сигнатуру у кеші API. Користувач надав URL і HTTP-статус, але не JSON-відповідь
сервера. Без доступу до схеми робочої БД неможливо відрізнити невстановлений SQL
від застарілого кешу. [Документація Supabase](https://supabase.com/docs/guides/api/rest/postgrest-error-codes).

## Один файл для встановлення

1. Відкрийте [profit-repair.sql](../supabase/setup/traffic-optimization/profit-repair.sql).
2. У потрібному проєкті Supabase відкрийте **SQL Editor → New query**.
3. Вставте весь файл і натисніть **Run**. Цей SQL не призначений для Edge Functions.
4. Після успішного виконання оновіть сторінку бухгалтерії та повторіть пошук
   за вибраним періодом у вкладці «Прибуток».

Файл об'єднує чинні визначення `traffic_profit_acts`,
`traffic_receipter_salaries`, `traffic_profit_labels` та двох JSON-помічників.
Залежності встановлюються перед читачами. Наприкінці виконується
`NOTIFY pgrst, 'reload schema'`, як рекомендує
[Supabase](https://supabase.com/docs/guides/troubleshooting/refresh-postgrest-schema).

Використовуються наявні таблиці, чинні права та RLS (`SECURITY INVOKER`).
Записи актів, зарплати, клієнтів і авто не змінюються. Фінансові формули,
фільтри дат, пакетний розмір відповідей і кешування фронтенду збережені.
Файл використовує `CREATE OR REPLACE FUNCTION`; повторний запуск дозволений
для цих чинних сигнатур. Якщо SQL завершується помилкою, транзакція відкочується.
