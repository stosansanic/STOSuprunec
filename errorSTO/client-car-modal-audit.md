# Аудит modal-content-create-sakaz_narad

Дата: 21.10.2026. Додавання, редагування, приховування автомобіля, вибір клієнта/авто,
відновлення за VIN, створення акта та передавання з планувальника.

## Поведінка автомобіля та історії

«Видалити» встановлює `cars.is_deleted = true` тільки для вибраного автомобіля.
Клієнт, його контакти, сам рядок автомобіля та старі акти не видаляються.
Приховане авто більше не відображається у звичайному списку вибору.

У режимі «Додати» точний VIN шукається серед активних і прихованих авто.
Приховане авто відновлюється з тим самим `cars_id`, отримує вибраного нового
власника та актуальні введені поля. Старі акти залишають попереднього клієнта;
історія сервісу читається за `cars_id`, тому попередні ремонти не губляться.
Нові акти матимуть нового клієнта. Номерний знак сам по собі не об'єднує автомобілі.

VIN порівнюється без пробілів і без урахування регістру. Пунктуація зберігається,
щоб різні історичні значення не зливалися. Дублікати VIN блокують автоматичне
відновлення з поясненням. Активний автомобіль спочатку треба вибрати або приховати
перед зміною власника. Авто без VIN можна додати, але автоматично пов'язувати його
з прихованим автомобілем за здогадкою система не буде.

## Виправлені проблеми

| Було | Стало |
| --- | --- |
| VIN перевірявся тільки серед активних авто поточного клієнта; приховане авто створювалося повторно. | Точний серверний пошук за VIN, відновлення старого ID, збереження історії. |
| Клієнт створювався до перевірки автомобіля, частина операції могла залишитися після помилки. | Клієнт і авто зберігаються в одній транзакції. |
| Редагування читало та повторно записувало весь JSON. | Лише змінені поля, початкові значення, перевірка конфліктів і коротке підтвердження. |
| DELETE-позначення не перевіряло власника чи фактичну зміну. | Перевірка вибраного ID, власника, початкової картки та результату операції. |
| Після приховування залишалися дані автомобіля у формі. | Автомобіль очищається, клієнт і контакти лишаються. |
| Вибір клієнта без авто міг залишити автомобіль попереднього клієнта. | Прив'язки очищаються до підтвердження нового вибору. |
| Запізніла відповідь могла заповнити змінену/закриту форму. | Перевірки поточного вибору, користувача, екземпляра модалки та введення. |
| Режим після повторного блокування міг не відповідати напису кнопки. | Спільний стан режимів, скидання індексу й узгоджене керування з інших модулів. |
| Під час підтвердження/запису можна було змінювати форму або повторно відправляти запит. | Контроли заблоковані, одна активна операція, перевірка незмінності підтверджуваної форми. |
| Після мережевої помилки додавання могло створити дублікат. | Повтор тієї самої спроби розпізнається сервером, включно з авто без VIN. |
| Створення акта робило INSERT та окремий PATCH приймальника. | Один RPC перевіряє активне авто/власника і записує приймальника разом з актом. |
| Прив'язка до планувальника могла перезаписати акт, призначений паралельно. | Умовне оновлення тільки порожньої або тієї самої прив'язки. |
| Збереження клієнта/авто перечитувало всі відкриті акти. | Локальне оновлення відповідних рядків із підтверджених полів. |

## Запити й трафік

- Відкриття модалки саме по собі не завантажує довідники.
- Підказки завантажуються сторінками до 20 записів; однакові одночасні запити
  об'єднуються. Повторний вибір у межах модалки використовує кеш без короткого TTL.
- Кеш обмежений за розміром, ізоляцією користувача та життєвим циклом форми.
  Повний отриманий результат дозволяє звузити пошук локально; неповний не видається
  за весь довідник. Помилка запису скидає кеш для наступного явного вибору.
- Вибір клієнта у заблокованій формі: один компактний RPC для клієнта й першого
  активного авто. У режимі редагування читається лише потрібний клієнт.
- Дані конкретного авто/клієнта містять поля форми та контактні телефони;
  зарплата, історія, сторонні JSON-розділи не передаються.
- Незмінена форма: нуль запитів запису. Збереження змін або приховування:
  один RPC; наявний журнал реальної операції рахується окремо.
- Звичайне збереження клієнта/авто не перечитує список актів. Якщо активний
  пошуковий фільтр залежить від зміненого ПІБ/авто, потрібне одне обмежене
  повторне читання результатів і підсумку, щоб не показувати старі збіги.
- Новий акт додається до відповідного поточного списку з підтвердження запису;
  якщо потрібних назв немає в пам'яті, читаються лише відсутні назви за ID.
