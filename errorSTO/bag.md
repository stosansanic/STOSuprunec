**Спільні вимоги, обов'язкові для кожного пункту**

1. До реалізації зафіксувати мережевий baseline на однакових даних: холодне відкриття, повторне відкриття, пошук, запис, дві вкладки, два користувачі, reconnect. Реєструвати сценарій, маршрут, таблицю/RPC, кількість викликів, кількість рядків, тривалість і розмір відповіді. Розділяти HTTP transferred bytes та розмір розпакованого JSON; не видавати розмір JSON за точний billed Egress. Не записувати токени, ключі, паролі, ПІБ, телефони, повні тіла запитів чи відповідей у діагностику. Не запускати повні експорти в продакшені для вимірювання.
2. Нижченаведені контракти — проектні назви та форми результатів, а не твердження, що відповідні RPC вже існують. Обрати прямий вузький SELECT, якщо його достатньо; RPC потрібен для спільної серверної фільтрації, проєкції JSON, агрегації або атомарної операції. Не переносити великий SELECT у Edge Function без зменшення відповіді PostgreSQL: це залишить PostgREST Egress між базою та функцією.
3. У кожного запиту має бути явний перелік потрібних полів. Спискова модель і повний документ — різні типи даних. Часткову відповідь не можна передавати у збереження як повний `data`, перезаписувати нею історію чи позначати нею повний offline snapshot.
4. Ключі кешу та pending-запитів: проєкт/організація, підтверджений обліковий запис, працівник, роль/область доступу, версія контракту, набір полів, нормалізовані фільтри й курсор. Зміна користувача/ролі/проєкту очищує або ізолює відповідні дані. Пізня відповідь старої сесії не потрапляє у нову. Не кешувати API-ключі/паролі разом із довідниками.
5. Єдиний запит, що вже виконується для однакового ключа, використовується всіма його споживачами. Видаляти pending-запис після помилки, дозволяти явний повтор. Для різних пошуків — debounce, скасування непотрібного запиту, якщо підтримується транспортом, та номер покоління, щоб запізніла відповідь не замінила поточну. Скасування на клієнті не гарантує, що сервер уже не виконав роботу.
6. Кешувати окремі записи, сторінки та довідники незалежно. Власний успішний запис оновлює відповідні ID; подія іншого клієнта оновлює або позначає неактуальними залежні запити. Після пропуску Realtime/відновлення мережі виконувати керовану перевірку актуальності потрібного набору. Не покладатися на Realtime як на гарантований журнал усіх змін. Без надійного `updated_at`/ревізії та обліку видалень не оголошувати повноцінну delta-синхронізацію реалізованою.
7. Базові розміри: списки 50 записів за запит, підказки 20, групи ID до 200; інший розмір дозволений лише за обґрунтованим контрактом. Порядок стабільний з унікальним ID як останнім ключем. Курсор/`has_more` забезпечує доступ до всіх збігів. Нуль збігів, мережева помилка та часткове завантаження — різні стани. Не вважати коротку сторінку кінцем, якщо її міг обрізати менший серверний ліміт; контракт має явно визначати завершення.
8. Загальні лічильники/суми обчислювати за повним фільтром на сервері, а не за першою сторінкою. Дані поза видимою сторінкою залишаються доступними через пошук і наступні сторінки. Не звужувати без пояснення поточні режими «усі», «закриті», «заморожені» або історичний період.
9. Зберегти діючі правила нормалізації ПІБ, каталогу, номерів, JSON-форматів, часових меж та округлення. До перенесення логіки на сервер створити таблицю відповідності старої та нової поведінки, включно з legacy `data` у формі рядка/об'єкта. Некоректний запис повинен дати контрольований результат, а не зірвати всі сторінки чи непомітно зникнути з підсумку.
10. Сервер перевіряє доступ при кожному читанні й записі. Переданий із браузера `employee_id`/роль не є достатнім доказом повноважень. Застосовувати чинний перевірений контекст автентифікації та працівника; якщо він не дозволяє безпечно викликати новий контракт, спочатку визначити перевірку. RPC не має обходити RLS/доступ через `SECURITY DEFINER`; для необхідних привілейованих функцій — явна серверна перевірка, обмежені GRANT і search_path. Service-role ключ у браузер не передавати.
11. Вимоги «0 повторних читань» нижче стосуються однакового актуального набору, того самого користувача й стабільної мережі без чужих змін. Перевірки автентифікації/блокування та обґрунтоване оновлення після зміни рахуються окремо. Свіжість залишків і фінансовий запис не довіряють довгому TTL — рішення про запис перевіряється сервером атомарно.
