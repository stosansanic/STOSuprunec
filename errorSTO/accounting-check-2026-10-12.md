# Перевірка бухгалтерії — 12.10.2026

## Межі перевірки
Перевірено локальний код шести вкладок та виконано тести читання, розрахунків, пагінації, захисту виплат і SQL на ізольованій PGlite. Робочу базу не змінювали; фактична відповідь HTTP 500 з production ще не отримана. Це не підтвердження працездатності всіх сценаріїв у production.

| Вкладка | Результат локальної перевірки |
|---|---|
| 🏪 Склад | Тести серверної пагінації, загальних сум, дат, конкурентного редагування та повторних виплат пройшли. |
| 👨‍🔧 Зарплата | SQL на тестових даних працює, включно з понад 1000 актами, TEXT/JSON та RLS. Помилку 500 не відтворено. Виправлено втрату message/code у звичайному об'єкті помилки PostgREST. |
| ⚙️ Деталі | Тести спільної серверної вибірки, фільтрів, сум, кешування та відхилення застарілої відповіді пройшли. |
| 💰 Прибуток | Тести читання всіх сторінок, пов'язаних клієнтів/авто та зарплат приймальників пройшли. |
| 📊 Аналітика | Тести агрегатів, дат, персоналу, RLS-сумісного читання та інвалідації кешу пройшли. |
| 📝 Лог дій | Виправлено старі записи у локальному масиві після порожньої відповіді/помилки; повідомлення сервера виводиться через textContent. Регресійні тести пройшли. Залишається поточна межа останніх 500 записів, фільтри застосовуються до них. |

## Підтверджені помилки
1. HTML CSP бухгалтерії блокувала apis.google.com, хоча Vercel CSP дозволяла. Додано точні Google origins для script/connect/frame, без wildcard і без вимкнення CSP.
2. PostgREST повертає plain object. Зарплата перетворювала його на [object Object], приховуючи причину. Тепер повідомлення містить код і текст сервера; details/hint зберігаються. Автоповторних запитів не додано.
3. Лог дій зберігав попередній auditRawData після порожнього результату і збою. Фільтр міг повторно показати старі записи. Масив тепер очищається.

## Що ще потрібно для 500
DevTools → Network → traffic_payroll_report → Response: потрібні code/message/details. Поки немає цих даних, неможливо обґрунтовано вибрати виправлення між SQL timeout, помилкою даних, схемою або залежностями. Валідація SQL навмисно відхиляє дублікати актів/робіт та неправильну структуру історії; прибирати її для маскування 500 не можна. Відсутність регресії на синтетичних даних не виключає збою на реальній історії.

Повідомлення content.js, globals-front.js, adblock-picreplacement.js схожі на помилки розширень. Перевірити URL джерела (chrome-extension:// або інший extension origin) та відтворити без розширень. Без URL не можна категорично приписати кожну помилку розширенню.

## Публікація
Ці зміни потребують оновлення frontend на Vercel. Нової SQL-міграції не створено: причина production 500 ще не підтверджена. Виправлення CSP саме по собі не виправляє RPC зарплати.
