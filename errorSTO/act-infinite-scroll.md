# Автоматичне підвантаження актів

11.10.2026. Початково таблиця показує 50 актів. Коли у видимій області з’являється 45-й із 50 актів, наступний запит повертає до 5 актів (разом 55). Далі поріг — 50-й із 55, 55-й із 60 тощо; рядки додаються знизу. Кнопки сторінок прибрані. Бейдж зберігає загальну кількість за фільтром. Після зміни пошуку/сортування/фільтра починається новий список. Повторні ID не додаються; запізнілі відповіді попереднього списку відкидаються. При помилці показується окрема кнопка повтору запиту без автоматичного циклу повторів.

Порядок встановлення:

1. Виконати `supabase/migrations/20261011121131_traffic_act_infinite_scroll.sql` у SQL Editor після пакета `traffic_act_search`. Зручна копія: `supabase/migrations-by-date/10.11.26/Інші міграції/20261011121131_traffic_act_infinite_scroll.sql`.
2. Розгорнути frontend на Vercel. Для цього виправлення Edge Functions не потрібні.

Міграція додає RPC `traffic_act_search_page_v2`, який приймає розмір 5 або 50. Старий RPC лишається для попереднього frontend. Нових таблиць немає. Права читання залишаються `security invoker` з RLS.

Production не змінювався. Пагінація використовує поточне сортування та offset: паралельні вставки/видалення можуть зсунути список, як і раніше; повторне оновлення таблиці перебудовує його. Не вважається незмінним знімком бази.

## Збереження поточного акта

`refreshActRowInTable` більше не викликає `loadActsTable` для списку з підвантаженням. Читається один акт за `act_id` і пов'язані з ним клієнт/авто. Оновлюється лише його рядок; решта завантажених рядків і позиція підвантаження зберігаються. Якщо акт перестав відповідати стану/датам/пошуку, прибирається лише цей рядок, а лічильник і наступний offset коригуються. Запізніла відповідь після зміни фільтра чи користувача не застосовується.

TypeScript і 7 цільових перевірок пройшли, включно зі збереженням 55 завантажених актів, зміною статусу та запізнілою відповіддю. Для цього додаткового виправлення потрібне лише оновлення frontend; нової SQL-міграції й зміни файла №8 немає.
