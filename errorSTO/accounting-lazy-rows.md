# Ліниві списки бухгалтерії — 12.10.2026

## Поведінка

- Кнопки попередньої/наступної сторінки зарплати й деталей прибрані.
- Початкова кількість рядків визначається висотою видимої області таблиці. Якщо висота рядка ще невідома, використовується початкова оцінка; після відображення контролюється фактичне положення рядків.
- Коли у видимій області опиняється один з останніх десяти рядків, додається наступна порція із десяти. Для резерву біля нижньої межі можливе додаткове підвантаження одразу після відкриття.
- Перевіряється саме прокрутка вкладеної таблиці на комп'ютері або сторінки на телефоні. Приховані вкладки нічого не підвантажують.
- Одночасно виконується один запит конкретного списку; після помилки автоматичне повторення зупиняється. Є кнопка повторення невдалого завантаження, без кнопок перемикання сторінок.
- При додаванні рядків наявні незмінені DOM-рядки зберігаються. Зміна фільтра створює новий набір, застарілі відповіді ігноруються.

## Звідки надходять рядки

| Вкладка | Джерело при прокрутці |
| --- | --- |
| Зарплата | SQL повертає спочатку кількість під видиму область, далі до 30 у буфер; на екрані додається по 10 із буфера |
| Деталі по актах | Аналогічно, через чинний RPC з параметром `p_limit` |
| Журнал | SQL повертає до 30 після початкової області; показ по 10, курсор — дата та ID останнього отриманого запису |
| Склад / магазини | По 10 рядків із кешу вже вибраного періоду |
| Прибуток / витрати | По 10 рядків із кешу вже вибраного періоду |
| Аналітика | Агреговані графіки й короткі рейтинги зберігають наявну поведінку; перемикання сторінок там немає |

**Межа цієї зміни:** початкове читання періоду складу й прибутку не переведене на серверні порції по 10. Ці модулі обчислюють підсумки й фільтри на клієнті з повного кешу періоду. Тут введено ліниве відображення, а не зменшення першої SQL-вибірки. Перенесення їхніх фінансових формул, фільтрів і підсумків у SQL потребує окремої зміни. Звуження вже завантаженого періоду, як і раніше, працює локально.

## Зменшення кількості запитів

Після уточнення пріоритету розмір мережевого пакета відокремлено від кроку відображення. Пакет до 30 рядків використовується тільки коли для продовження прокрутки закінчилися вже прочитані рядки. Наступні дві порції по 10 не потребують нового RPC. Для перегляду наступних 30 рядків це один запит замість трьох (без урахування першого завантаження, зміни фільтра та явного оновлення).

Це компроміс: якщо користувач припинить прокрутку, частина невеликого буфера може залишитися невикористаною. Гарантувати таке саме зниження обсягу трафіку не можна. Зменшується кількість повторних відповідей із метаданими та фрагментами одного акта; економія в байтах залежить від даних і дій користувача.

Excel-експорт повторно використовує вже отримані діапазони зарплати й деталей замість примусового очищення кешу. Масові оплати продовжують отримувати актуальні початкові стани перед записом. Розмір видимого списку не обмежує суми, експорт або набір для масової оплати.

Додаткового SQL для буфера не потрібно: попередня міграція підтримує змінний розмір відповіді до 200 рядків. Файл №8 вже містить необхідний серверний контракт.

## Суми, оплати, експорт

- Серверні підсумки зарплати й деталей охоплюють усі результати, а не лише завантажений початок.
- Масова оплата, як і раніше, явно дочитує весь набір і зберігає перевірки конкурентних змін.
- Excel-експорт зарплати й деталей явно дочитує всі відповідні сторінки. Для складу/прибутку використовує повний кеш. Початкові DOM-рядки відновлюються після формування файла.
- Локальне приховування рядка деталей не змінює серверний курсор і базові підсумки для перевірки наступної порції.
- Різні розміри сторінок враховуються в ключах кешу; локальне звуження зарплати/деталей допускається лише при повному покритті попереднього результату.

## Встановлення

1. На чинній базі після попередніх бухгалтерських міграцій виконати `supabase/migrations/20261012133426_traffic_accounting_lazy_rows.sql` у **Supabase → SQL Editor**. Це SQL, не код Edge Function. Файл також включає попереднє виправлення тайм-ауту зарплати.
2. Розгорнути оновлений фронтенд на Vercel.
3. Для нових проєктів зміна включається в файл №8 та зведений пакет читання.

Нових таблиць немає. Використовуються чинні RLS та `SECURITY INVOKER`. Міграцію в робочій базі автоматично не виконано. TypeScript перевіряється компіляцією; браузерні сценарії, автоматичні тести та виконання SQL на сервері цього разу не запускались.
