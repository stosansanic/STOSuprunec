## Зміна кількості й зарплати оплаченої роботи — 20.10.2026

Цей пакет розширює попереднє виправлення ціни: поточне нарахування можна
змінювати, а вже підтверджені виплати зберігаються окремо.

1. Виконайте весь [payroll-payment-ledger-repair.sql](payroll-payment-ledger-repair.sql)
   у **Supabase → SQL Editor** чинного проєкту з попереднім пакетом №8.
2. Опублікуйте оновлений frontend на Vercel та перезавантажте відкриті вкладки.
3. Заново відкрийте акт, перевірте потрібні кількість і зарплату та збережіть.
   У бухгалтерії буде видно нарахування, виплачену суму, доплату або переплату.

При першій зміні оплаченої роботи її попередня зарплата й дата виплати
стають початковою подією в `__payroll_payments`. Наступні збереження акта
зберігають ці події. Зарплата рядка є загальною сумою: повторного множення
на кількість немає. Наприклад, після зміни зарплати `25 → 40` виплачено
залишається `25`, а до виплати — `15`. При зміні `25 → 10` переплата — `15`;
автоматичної виплати або повернення грошей не відбувається.

Перерахунок комісії вже оплаченого приймальника також зберігає його попередню
виплату. Перенесення оплаченої роботи іншому працівнику, видалення,
неоднозначні старі рядки без ID і зміна історії виплат через збереження акта
залишаються захищеними.

Доплата записується лише на суму боргу. Явне скасування позначки останньої
виплати залишає початкову подію та додає подію анулювання. Звіт за датою
виплати рахує чинні виплати вибраного періоду, а не поточну зарплату.
Історію не потрібно завантажувати окремим запитом: вона надходить у наявному
фрагменті відповідного акта.

Міграції самі не перераховують робочі акти й не проводять виплат. Для нового
проєкту весь код включено до єдиного
`D:/Alim/Proekt/Основа проектів/8 зменьшує вихідний трафік.sql`;
окремо цей пакет після оновленого №8 не потрібен.
Перегенерація локальних SQL-копій: `node scripts/prepare-payroll-ledger.cjs`.

## Корекція ціни оплаченої роботи — 20.10.2026

Це попереднє, вужче виправлення. Для зміни кількості й зарплати використовуйте
`payroll-payment-ledger-repair.sql` із розділу вище: він уже включає виправлення
ціни та замінює описані нижче обмеження щодо кількості й зарплати.

Для чинного проєкту з установленим `payroll_pending_recovery`:

1. Виконайте весь [payroll-paid-price-repair.sql](payroll-paid-price-repair.sql)
   у **Supabase → SQL Editor**, перед публікацією нового frontend.
2. Опублікуйте оновлений frontend на Vercel.
3. Заново відкрийте відповідний акт і натисніть **«Зберегти зміни»**.
   Після успішної синхронізації акт можна закрити.

Виправлення дозволяє оновити ціну для клієнта в зарплатному записі вже оплаченої
роботи, коли її ID, виконавець, кількість, зарплата та виплата залишаються тими
самими. Наприклад, у акті №1274 ціна `1 → 50` більше не блокує синхронізацію
зарплати `25` з виплатою `17.10.2026`. Якщо поле «Сума» вже існує, воно
оновлюється відповідно до ціни та кількості.

Змінена зарплата, виконавець, кількість або видалення оплаченої роботи
залишаються причиною зупинки. Міграція змінює перевірку, а дані актів
і працівників сама не перезаписує. Вона містить перевірку на синтетичних даних,
яка скасовує встановлення, якщо захист виплат не працює.

Збереження використовує наявний зарплатний запит та перевірку паралельних змін.
Перезаписуються лише змінені зарплатні фрагменти працівників за поточним актом;
повна зарплатна історія не завантажується. Додаткових запитів це виправлення
не додає.

Для нових проєктів SQL уже включено до єдиного файлу
`D:/Alim/Proekt/Основа проектів/8 зменьшує вихідний трафік.sql`.
Окремо повторювати цей пакет після файлу №8 не потрібно.

## Склад і «Прибуток»: серверні підсумки та порції рядків — 15.10.2026

Для чинного проєкту, в якому вже встановлено попередній пакет №8:

1. Виконайте весь [accounting-pages.sql](accounting-pages.sql) у **Supabase → SQL Editor**.
2. Після успішного виконання опублікуйте оновлений frontend на Vercel.

Це дві міграції з папки `supabase/migrations-by-date/10.15.26`, об'єднані в один
transaction. Пакет додає функції звітів і захищеної масової оплати, а також
потрібні індекси дат. Саме виконання міграції не проводить оплат, не змінює
фінансові записи та не замінює їхні RLS-політики.

Перше читання повертає підсумки всього вибраного результату та порцію рядків.
Склад отримує по 40 рядків, «Прибуток» — по 30. Повторні однакові запити
використовують кеш; одночасні однакові читання об'єднуються в один запит.
Наступні порції не передають підсумки повторно; інтерфейс показує по 10 рядків
із кешу. Весь результат дочитується лише під час явного експорту. Масова оплата
перевіряє підтверджений набір і суми та обробляє його незалежно від прокрутки.
Нові записи, створені паралельно після перевірки, не додаються до підтвердженої оплати.

Контрольний відбиток у відповідях виявляє зміни між порціями. Звіт не змішує
рядки з різних версій. Глобальні блокування, нові таблиці та фонове опитування
для цього не додаються. Підрахунки й контрольний відбиток потребують обробки
вибраного періоду всередині PostgreSQL; економиться насамперед передавання даних
і кількість звернень браузера. Це не усуває серверні обчислення.

У «Прибутку» контрольний відбиток охоплює фінансові дані. Підписи клієнта й авто
читаються лише для поточної порції, якщо ввімкнено відповідні колонки.
Перейменування клієнта/авто в іншому браузері між порціями може змінити підпис
у наступній порції; підсумків це не змінює.

Перегенерувати пакет і копії за датою: `node scripts/prepare-accounting-pages.cjs`.
Для нового проєкту ці ж визначення включаються в єдиний файл №8 після попередніх
залежностей; окремо повторювати пакет тоді не потрібно.

## Незавершена зарплата: акт збережено, нарахування очікує синхронізації

1. Виконайте весь [20261013105659_payroll_pending_recovery.sql](../../migrations/20261013105659_payroll_pending_recovery.sql)
   у **Supabase → SQL Editor**, перед публікацією нового frontend. Це не Edge Function.
   Потрібні чинні `payroll_fragments`, `act_editor_lease_guard`, `traffic_payroll_employees`.
   Нових таблиць і автоматичного перерахунку в міграції немає.
2. Опублікуйте frontend на Vercel.
3. Закрийте редактори відповідних актів. Відкрийте **Бухгалтерія → Зарплата →
   Переглянути акти → Відновити нарахування**. Є окреме відновлення та пакет до 25 актів.

Сам акт раніше записувався перед зарплатою. Помилка на наступному кроці залишала
`__payroll_pending=true`; той самий маркер використовується при розмороженні та
офлайн-відновленні. Лічильник охоплює всі незаморожені акти незалежно від дат звіту.
Число «7» саме по собі не вказує на причину для кожного запису.

Тепер нарахування спочатку обчислюються в локальній сесії, потім зарплата всіх
працівників за один акт та зняття pending записуються однією транзакцією.
Сам акт і склад зберігаються раніше, окремо від цієї транзакції.
За будь-якого конфлікту зарплатний пакет відкочується; біля номера показується причина.
Повторний запуск не створює дублікати. Закриті акти відновлюються без зміни дати закриття;
заморожені та відкриті в редакторі акти пропускаються з поясненням.

Оплачені суми, роботи, виконавці, дати зарплатних записів та ознаки виплати захищені.
Неоднозначні старі роботи без ID і зміна старих сум без даних початкового розрахунку
зупиняють автоматичне відновлення. Не скидайте pending вручну: це дозволить виплати
без підтвердження нарахувань. Для таких записів спочатку потрібно звірити суму та виконавця.

Зчитуються лише зарплатні фрагменти конкретного акта, компактні дані працівників,
потрібний склад, клієнт та авто. Перелік актів завантажується сторінками по 50.
Production SQL та конкретні 7 актів у цій сесії не змінені: доступу до Supabase немає.
Локальні `npm run check` та `npm run build:vercel` проходять; це не підтверджує встановлення міграції.
Міграцію також включено до файлу №8 у `D:/Alim/Proekt/Основа проектів`; для чинного
проєкту поруч є окремий `8.2 Відновлення зарплати.sql` з таким самим кодом.

## Порядок встановлення

1. Звірте фактичну схему та права потрібного проєкту. Локальний шаблон «Основа проектів» прочитаний для сумісності, але його не потрібно виконувати: він містить повне створення бази й інші операції.
2. У **Supabase → SQL Editor** виконайте весь [install.sql](install.sql). Це SQL, а не вміст Edge Function index.ts. Пакет створює/оновлює функції читання над наявними таблицями, одним transaction. Він не створює таблиць і не видаляє історію.
3. Встановіть окремі міграції запису зі списку нижче. Вони навмисно не включені у пакет читання.
4. Розгорніть відповідні змінені Edge Functions, потім frontend. Перед frontend усі необхідні RPC повинні вже бути встановлені.
5. Перевірте акти, склад, зарплату, магазинні розрахунки, планування, аналітику та Нову пошту під фактичними ролями. Для Network використовуйте невеликий контрольований сценарій, а не повний експорт робочої бази.

Не виконуйте всі історичні міграції з папки migrations: там є попередні версії інтеграцій та сторонні зміни. При помилці install.sql його transaction відкотиться; потрібно виправити сумісність схеми, а не видаляти таблиці.

Порядок після install.sql, до frontend:

5. 20261011080000_payroll_fragments.sql — атомарні зарплатні фрагменти, перевірки baseline і повтору.
6. 20261011100000_reminder_delivery_claims.sql — claims/lease на наявних таблицях нагадувань; додає службові стовпці та індекси, без нових таблиць.

Файли розташовані у supabase/migrations. Нових баз і видалення історії немає. Без необхідної write RPC відповідний запис показує помилку, а не запускає прихований старий INSERT.

## Edge Functions і нагадування

- nova-poshta: актуальний index.ts разом із імпортами; SQL Editor не розгортає TypeScript.
- check-reminders і змінені спільні модулі доставки: розгортати після reminder_delivery_claims.
- Фактичні встановлені cron можна прочитати через supabase/diagnostics/reminder_delivery_audit.sql та inspect-runtime.sql. Файли не виводять команди cron або секрети.
- Подієві правила browser new/old збережені: SQL polling не відтворює проміжні події. Доставки в обох шляхах мають атомарний claim. Невизначений результат відправлення не повторюється автоматично; контрольований повтор вимагає підтвердження недоставки.

## Права, сумісність та відкат

Нові функції читання працюють як SECURITY INVOKER під чинними правами й RLS. Вузька серверна перевірка Нової пошти доступна service_role. Передані клієнтом ID не замінюють доступ PostgreSQL. Фактичні production policies потрібно перевірити окремо.

Частина старих читачів має fallback лише для відсутньої RPC; нові критичні контракти вимагають SQL і показують явну помилку. Помилки прав/мережі не вважаються дозволом на широкий fallback. Тому SQL встановлюється перед frontend.

Повторне встановлення read-only пакета перевіряється локальними тестами. Для відкату frontend можна повернути попередню версію: додаткові читачі не видаляють даних. Write-міграції змінюють правила запису, тому їх відкат потребує окремого перегляду; не видаляйте функції або службові поля навмання.

## Локальна перевірка

- Перегенерація пакета: node scripts/prepare-traffic-sql.cjs. Скрипт збирає тільки *_traffic_*.sql і не підключається до бази.
- TypeScript: npm run check. Збірка: npm run build:vercel.
- SQL/RLS, пагінація, фінансові формули й конкурентні записи перевіряються у tests через ізольовану PGlite. Браузерний тест Нової пошти працює із вигаданими локальними даними та блокує зовнішні запити.
- Поточний результат тестів та незавершені вимоги: [implementation-status.md](../../../errorSTO/implementation-status.md), [bag.md](../../../errorSTO/bag.md).

Локальні тести й розмір JSON не є вимірюванням billed Egress. Фактичну економію можна підтвердити після встановлення за однаковими робочими сценаріями й Supabase Usage.

## Ліниве відображення бухгалтерії — 12.10.2026

Перед оновленням frontend виконайте [20261012133426_traffic_accounting_lazy_rows.sql](../../migrations/20261012133426_traffic_accounting_lazy_rows.sql) у SQL Editor. Вона включає попереднє виправлення зарплати й дозволяє читати зарплату та журнал зі змінним розміром порції. Початкова порція — під видиму область; наступні мережеві пакети — до 30, показ із кешу по 10. Деталі використовують наявний параметр `p_limit`. Це зменшує частоту запитів під час прокрутки; для буфера нової міграції не потрібно. У складі й прибутку ліниве відображення використовує повний кеш вибраного періоду; їхні початкові SQL-вибірки ця зміна не скорочує.

[Поведінка прокрутки, експорт і межі оптимізації](../../../errorSTO/accounting-lazy-rows.md). Актуальні `install.sql` і файл №8 містять міграцію.
