АТЛАС: ОПТИМІЗАЦІЯ ФОНОВИХ НАГАДУВАНЬ — 23.10.2026

ЧИННИЙ ПРОЄКТ
1. У Supabase відкрийте потрібний проєкт → SQL Editor → New query.
   Вставте ВЕСЬ файл «9.4 Атлас — фонові нагадування.sql» і виконайте.
   Очікувано: Success. У разі помилки не переходьте до наступного кроку.
   Пакет виконується однією транзакцією; необхідні залежності доставки включено.

2. Edge Functions → check-reminders → Code → index.ts.
   Замініть ВЕСЬ код вмістом «02-check-reminders-index.ts» із цієї папки → Deploy.
   Це повний TypeScript із локальними залежностями. Його не вставляють у SQL Editor.
   Не створюйте другу функцію з іншою назвою. Залиште чинні Secrets та налаштування
   авторизації функції: збережена команда Cron використовує ті самі адресу й заголовки.
   nova-poshta для цієї оптимізації оновлювати не потрібно.

3. Опублікуйте оновлений сайт звичним способом. Перезавантажте відкриті вкладки.
   Важливий порядок: SQL, потім check-reminders, потім сайт.
   Локальна зміна файлів сама по собі не змінює функцію в Supabase.

4. За потреби виконайте «Перевірка встановлення.sql»: це лише читання,
   без запуску нагадувань і без показу секретів.
   Після встановлення створіть тестове нагадування на найближчі 2 хвилини
   з каналом «Обидва»: Telegram має прийти незалежно від відкритого браузера,
   а повідомлення в програмі — після відкриття/активації вкладки адресата.

НОВИЙ ПРОЄКТ
Встановлюйте основні файли проєкту у звичному порядку, включно з базовим 1.1
(таблиці Атласу, Cron, функції розкладу) та оновленим повним файлом 8.
Повторно запускати окремий 9.4 після нового файлу 8 не потрібно.
Для check-reminders беріть актуальний повний код із цієї папки або з оновленого
«9.1 НП Index Edge Functions → check-reminders..sql» у папці шаблонів.
Попри історичне розширення .sql, цей файл 9.1 містить TypeScript для Edge Functions.
Адреса Supabase у settings, рядок 18, має відповідати саме новому проєкту.
Налаштування Telegram та прив'язки адресатів залишаються потрібними, як раніше.

ЩО ЗМІНИЛОСЯ
• Cron перевіряє наявність роботи всередині БД щохвилини. Для майбутніх
  нагадувань він не викликає HTTP/Edge. Якщо активних завдань немає — job видаляється.
• SQL-умови «Контроль» як і раніше перевіряються сервером; незмінений результат
  передається короткою ознакою без повторного масиву рядків. Сам SQL продовжує
  виконуватися: умови можуть залежати від поточного часу, їх не можна сліпо кешувати.
• Вкладки більше не запускають щохвилинні HTTP-перевірки Telegram.
• Службові leases зберігаються в закритій таблиці без Realtime, а не змінюють
  atlas_reminders двічі при кожній перевірці.
• Сервер зберігає окрему доставку в програму для кожного адресата. Черга читається
  сторінками по 20 за входом, поверненням до вкладки, Realtime-подією та перепідключенням.
  Після помилки використовується відкладена повторна спроба; при прихованій вкладці
  HTTP-читання черги не відбувається. Невідправлений claim відновлюється після lease.
• Telegram і програма мають незалежні захисти від дублів. Вже почату доставку
  з невідомим результатом не надсилаємо повторно навмання.
• Зміна правила під час обробки не дозволяє старому обробнику пересунути розклад.
• Для фонового моніторингу браузер завантажує лише JSON-правила подій свого
  адресата, сторінками по 100, без SQL-результатів із meta та без майбутніх нагадувань.
  Черга фактичних повідомлень фільтрується окремо за адресатом, сторінками по 20.
• JSON-правила подій у програмі зберігають Realtime. Для повідомлень із повним
  описом змін зберігаються потрібні поля: обрізання їх змінило б зміст повідомлення.

Перевірки виконувалися локально на ізольованій БД і підставних транспортних відповідях.
Жодних реальних Telegram-повідомлень перевірки не надсилали.
Фактичний трафік production після встановлення слід порівняти в Supabase Usage.
Черга використовує наявні журнали нагадувань; наявні строки очищення історії збережено.
