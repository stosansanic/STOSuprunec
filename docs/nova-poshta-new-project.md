## Що знаходиться в цій папці

- `01-update-existing.sql` — оновлює функції, додає act_ids та індекси до вже встановленої таблиці `public.novaposhta`. Не створює базу або таблиці. Для поточного проєкту з наявним архівом виконай цей файл повністю в новому запиті SQL Editor.
- `01-database.sql` — налаштовує `settings.novaposhta`, `acts.novaposhta`, функції доступу та захисні тригери. Створює одну таблицю `novaposhta` для повних даних ТТН та історії змін. Не створює таблиць `np_*`, не видаляє старі дані.
- `02-secrets.env` — ключ шифрування лише для цього Supabase-проєкту.
- `03-index.ts` — повний код Edge Function, готовий для вставлення в Dashboard; додаткові файли імпорту не потрібні.
- `README.md` — ця інструкція.

## Встановлення в поточному проєкті

1. Відкрий потрібний проєкт у Supabase. Назва цієї папки — його Project Ref.
2. SQL Editor → New query: встав увесь `01-database.sql` і натисни Run. Повторний запуск зберігає наявні налаштування й ТТН.
3. Edge Functions → Secrets: додай `NP_ENCRYPTION_KEY` зі значенням із `02-secrets.env`. Якщо в проєкті вже працює Нова пошта, збережи саме раніше встановлений ключ. Він потрібний для читання збережених пароля й API-ключа.
4. Edge Functions: створи або відкрий функцію `nova-poshta`. Заміни весь `index.ts` вмістом `03-index.ts`, вимкни **Verify JWT / Enforce JWT verification** у налаштуваннях функції та натисни Deploy. Функція самостійно перевіряє Supabase JWT і доступ працівника. У Dashboard має бути доступний серверний ключ Supabase; він не додається до браузерного `.env`.
5. Опублікуй frontend цього репозиторію, налаштований на той самий Supabase-проєкт.
6. У програмі відкрий «Нова пошта», підтвердь пароль працівника СТО. Адміністратор у налаштуваннях вводить телефон, API-ключ, за потреби логін і пароль НП. Вони зберігаються у `settings.novaposhta`; пароль і ключ зашифровані.
7. Натисни «Оновити з Нової пошти», щоб наповнити архів. Звичайне відкриття списку й деталей читає тільки базу. За замовчуванням «Створено від» і «Створено до» охоплюють останні 14 календарних днів, включно із сьогоднішнім, за часом Києва. Запит до НП охоплює лише цей період, включно з обома днями. Якщо результат має кілька сторінок, завантажуються сторінки лише вибраного періоду. Якщо обидві дати очищено, застосовується той самий період останніх 14 днів. Якщо заповнена лише одна дата, потрібно вказати другу. Кожна отримана ТТН зіставляється з архівом за номером: нова додається, змінена оновлюється, однакова відповідь не спричиняє повторного запису. Окремого обходу всіх номерів архіву немає. Окремий номер можна завантажити через «Перевірити ТТН» → «Оновити з Нової пошти».
8. В акті через «ТТН цього акта» додай збережені номери. `acts.novaposhta` містить лише масив номерів, наприклад `["20400000000001","20400000000002"]`. Номери прив’язаних актів зберігаються в `novaposhta.act_ids` (bigint[]). Деталі посилок читаються з архіву `novaposhta`. Видалення зв’язку з актом не видаляє архів.

## Збереження історії

`novaposhta` містить: `ttn` (унікальний номер), `data` (поля для інтерфейсу), `raw_document` і `raw_tracking` (повні останні відповіді API), `history` (отримані зміни з часом), `direction`, `state`, `document_date`, `first_seen_at`, `last_seen_at`, `updated_at`. Нова таблиця одна; налаштування залишаються в `settings.novaposhta`.

Якщо НП не повернула номер або повідомила, що його не знайдено, збережені дані залишаються. Порожні поля часткової відповіді не стирають раніше отримані значення. Історія накопичується від моменту встановлення: події, які НП вже видалила до першого завантаження, відновити неможливо. Зберігаються всі поля, які API повертає для налаштованого акаунта.

Для оновлення чинної інсталяції з таблицею `novaposhta` виконай повністю `01-update-existing.sql`, потім кроки 4 і 5. Окрема міграція архіву: `supabase/migrations/20261003000000_nova_poshta_archive.sql`; вона потребує попередньо встановленого `supabase/setup/nova-poshta.sql`. Комплект `01-database.sql` уже включає обидва файли.

## Перенесення в новий проєкт СТО

Комплект — доповнення до цієї системи СТО. У новому Supabase спочатку мають існувати базові `settings`, `acts`, `slyusars`, `whitelist`, авторизація та RPC `verify_slyusar_password`. Потрібні ті самі стовпці й ролі, що в основному проєкті. Це не SQL для створення всієї системи з порожньої бази.

1. Скопіюй код репозиторію та встанови залежності (`npm install`). Локальну папку `supabase/dashboard-nova-poshta.local` між різними проєктами не копіюй.
2. Налаштуй `.env` і `.env.local` на новий Supabase URL та браузерний ключ. Для загального налаштування системи використовуй `setup_new_project.ps1`: він також готує комплект Нової пошти для URL із `.env`.
3. Для окремої генерації виконай у корені репозиторію:

   ```powershell
   node scripts/prepare-nova-poshta-dashboard.cjs https://НОВИЙ_PROJECT_REF.supabase.co
   ```

   Заміни `НОВИЙ_PROJECT_REF` реальним ідентифікатором Supabase (20 символів). Можна передати лише ідентифікатор без URL. Без аргументу використовується `VITE_SUPABASE_URL` із середовища, потім `.env.local`, потім `.env`.

4. У `supabase/dashboard-nova-poshta.local/НОВИЙ_PROJECT_REF` з'явиться окремий комплект із новим ключем. Виконай кроки встановлення вище для нового проєкту.
5. Додай працівників і дозволені email у новій системі та введи налаштування її акаунта Нової пошти через інтерфейс.

Повторна генерація для того самого Project Ref оновлює SQL, серверний код та інструкцію, зберігаючи ключ шифрування. Генерація сама нічого не встановлює в Supabase і не публікує сайт. Файли з секретами залишаються в ігнорованій Git папці.

Для старої інсталяції видалення таблиць виконується окремим `docs/nova-poshta-remove-legacy.sql`. Для нового проєкту цей файл не потрібен.

## Оновлення окремих полів

Для наявної ТТН порівнюються також вкладені поля. Змінена сума оновлює лише відповідне поле; незмінені статус, вага й решта значень зберігаються. Початковий запис історії містить повний `payload`, наступні записи — `changes` та `data_changes` зі зміненими полями. Оновлення даних НП не переписує акт — у ньому залишаються тільки номери ТТН. Однакова відповідь не виконує UPDATE.

Оновлення JSONB логічно змінює окремі ключі, але PostgreSQL фізично створює нову версію рядка. API НП все одно повертає свою повну відповідь; цей механізм скорочує зайві записи й обсяг історії, а не розмір відповіді НП.

## Оптимізація запитів

Сторінка НП зберігається одним пакетним RPC (до 40 ТТН замість окремого HTTP-запиту на кожну). Порожні пакети не надсилаються в базу. Після завершення вхідного або вихідного списку наступні сторінки цього напрямку не запитуються. Налаштування читаються один раз у межах серверного запиту; права доступу перевіряються кожного разу.

За замовчуванням початкове завантаження читає всі збережені ТТН за останні 14 днів пакетами до 50. Прокрутка додає старіші записи по 10 через np_archive_list_v2, без точного COUNT усієї вибірки. Вибраний вручну інший діапазон дат залишається обмеженням. SQL-комплекти включають міграцію 20261011123102_nova_poshta_infinite_scroll.sql. Короткі деталі та списки ТТН акта не передають raw_document, raw_tracking і history. Повна історія читається після розгортання відповідного блоку. Дані для списку ТТН акта отримуються одним запитом з архіву.

Одночасні однакові запити читання у вкладці об’єднуються, з урахуванням користувача і сесії працівника. Після завершення запиту тимчасове об’єднання очищається; довготривалого кешування даних або прав немає. Індекси додаються до існуючих таблиць: дата/напрямок у novaposhta та лише номери ТТН в acts (без індексування повної історії). Нові таблиці або бази не створюються файлом оновлення.

## Додавання ТТН з акта

У формі «Записати ТТН в акт» поле ТТН показує збережені номери з `novaposhta` за всі дати, включно зі старими відправленнями та номерами, доданими вручну. Найновіші показуються першими. Пошук працює за частиною номера; «Ще…» відкриває наступні 20 варіантів. Відкриття форми не звертається до API Нової пошти. Свіжі відправлення спочатку завантажуються кнопкою «Оновити з Нової пошти».

Поле «Номер акта» пропонує `№ акта · ПІБ клієнта · автомобіль · держномер` і шукає за будь-яким із цих значень. Показуються лише відкриті, незаморожені акти, до яких працівник має право додавати ТТН. До запису передається номер вибраного акта. Якщо форма відкрита з конкретного акта, його номер уже заповнений і не змінюється. Ручне введення номера акта та ТТН підтримується.

Перші варіанти обох полів читаються одним запитом. Подальший пошук виконується після короткої паузи введення; повторне відкриття тієї самої підказки використовує результати в межах відкритої форми. Повні дані й історія ТТН для цього не завантажуються. Для встановленого проєкту онови `01-update-existing.sql`, Edge Function із `03-index.ts` і frontend. Функція підказок використовує наявні `novaposhta`, `acts`, `clients`, `cars`; нових таблиць немає.

Додавання виконується в одній транзакції: якщо ТТН відсутня в novaposhta, створюється запис із номером і напрямком; наявний запис з даними НП зберігається. Номер акта додається в novaposhta.act_ids, а лише номер ТТН — у наявний acts.novaposhta. Кілька ТТН підтримуються, повторне додавання не створює дубля. Деталі нової ручної ТТН можна отримати кнопкою оновлення в її картці. Пошук за актом охоплює всі дати, щоб знаходити також ТТН без дати створення від НП. Стовпець «Акт» показує дозволені працівнику номери з novaposhta.act_ids.

Оновлення також перетворює старі об’єкти в acts.novaposhta на рядки ТТН. Перед цим їхній повний вміст переноситься в історію novaposhta з позначкою act_migration, щоб зберегти старі примітки та копії. Повторний запуск не дублює зв’язки чи історію перенесення.
