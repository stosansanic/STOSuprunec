# Нова пошта: встановлення та перевірка

## Виправлення імпорту 02.10.2026

Перевірка користувача підтвердила: `getOutgoingDocumentsByPhone` і
`getIncomingDocumentsByPhone` зі звичайним `apiKey` повертають `success:true`
і по 5 відправлень у `data[0].result`. Параметр `system: "PA 3.0"` натомість
спричиняє 20000201204 на цьому акаунті. Попередні висновки про прострочений ключ
або обов'язковість OAuth для цих списків не підтвердились.

Сервер тепер імпортує обидва списки без `system`, використовує `DateFrom`,
`DateTo`, `Page`, `Limit`, номер із `Number` та опис із `CargoDescription`.
Період першого імпорту — останні 90 днів; спільна пагінація перевіряє обидва
напрямки й продовжується наступним циклом, доки обидва списки не стануть порожніми.
Після успішного імпорту метадані `incoming_capability` стають `automatic`.
Нова міграція для цього виправлення не потрібна. Для застосування треба оновити
`nova-poshta/index.ts` у Supabase з нового згенерованого `03-index.ts`.
Оновлення тексту frontend потребує його звичайного розгортання.

## Уточнення діагностики 01.10.2026

На акаунті користувача `getDocumentList` повернув успішний порожній список.
Кабінет використовує `getOutgoingDocumentsByPhone` з `TokenOAuth2` та `system: "PA 3.0"`.
Попередня проба з `apiKey` та цим `system` повернула 20000201204 навіть після заміни ключа.
Це не доводить недоступності методу зі звичайним API-ключем без `system`.

`scripts/diagnose-nova-poshta.ps1` тепер порівнює запити з параметром вебкабінету та без нього,
окремо перевіряє вхідний список, рахує вкладений `data[0].result` і показує лише числові коди
помилок, кількість записів та назви полів. Ключ вводиться приховано та не записується у файл.
Не переносити браузерні OAuth-токени у конфігурацію інтеграції.

Офіційна сторінка інтеграції: https://novaposhta.ua/for-business/cooperation/integration/ .
Детальний портал https://developers.novaposhta.ua/documentation не вдалося прочитати автоматично.
Автоматичне завантаження списків за телефоном ще не підтверджено на цьому акаунті.
Помилка авторизації лише імпорту більше не зупиняє перевірку вже доданих ТТН;
відмова авторизації під час самого трекінгу, як і раніше, потребує перепідключення.

## Поточний стан

Модуль реалізовано локально. Міграцію та Edge Function **ще не встановлено в робочому Supabase**; frontend також не опубліковано цією роботою. Supabase CLI повідомив `Access token not provided`. Реального API-ключа НП і контрольних ТТН не використовували. Кожен Supabase-проєкт має власні таблиці, користувачів, посилки й доступи.

Реалізовано спільний список посилок, картки, пошук і фільтри, зв’язки з кількома заказ-нарядами, персональні права, лічильник прибуттів і захист конкурентних змін. Підключення одне на цей проєкт СТО. Перевірка НП запускається вручну кнопкою «Оновити зараз». Відкриття розділу завантажує збережені дані без автоматичної синхронізації з НП. Якщо відкрито кілька пристроїв, блокування в базі пропускає лише одну синхронізацію.

Вхідні посилки додаються за ТТН. Автоматичний повний список вхідних за телефоном не підтверджено. Для вихідних підготовлено імпорт документів акаунта за останні 30 днів із продовженням пагінації наступним циклом. Доступність методів і точність полів/статусів треба підтвердити на реальному акаунті перед прийманням інтеграції.

## 1. Встановлення через Dashboard

Frontend бере URL і публічний ключ із `VITE_SUPABASE_URL` та `VITE_SUPABASE_KEY` у конфігурації проєкту. Edge Function бере URL і службовий ключ із середовища того Supabase-проєкту, куди її встановили. У коді Nova Poshta project ref не зашитий.

Перед кожним новим Supabase-проєктом установіть у його `.env` правильні `VITE_SUPABASE_URL` та `VITE_SUPABASE_KEY`, потім згенеруйте Dashboard файли:

```powershell
node scripts/prepare-nova-poshta-dashboard.cjs
```

Пакети `01-database.sql` і `01-update-existing.sql` включають `traffic_np_employee` та його залежність `traffic_json_object` для вузької перевірки працівника без зарплатної історії. Перед оновленням Edge Function виконайте відповідний SQL-пакет. Якщо цієї RPC немає, звичайний JSON ще підтримує вузький SELECT, але старий JSON, збережений рядком, повертає явну помилку встановлення замість завантаження повного документа працівника.

Щоб файли перебудовувалися самі після редагування `.env` або `.env.local`, відкрий окремий термінал у папці проєкту та запусти `npm run watch:nova-poshta-env`. Залиш його працювати, поки перемикаєш конфігурацію. Спостерігач читає лише `VITE_SUPABASE_URL`, не показує ключі й створює комплект для відповідного Ref. Зупини його через `Ctrl+C`.

Команда читає URL із `.env.local`, потім із `.env`, і створює файли лише для цього project ref у локальній ігнорованій папці `supabase/dashboard-nova-poshta.local/<project-ref>/`. Не переносіть ці згенеровані файли до іншого проєкту: спочатку замініть URL у `.env` і запустіть команду знову.

Виберіть потрібний Supabase-проєкт у Dashboard. У **SQL Editor** відкрийте й виконайте згенерований `01-database.sql`. Він встановлює відсутню схему або зберігає вже наявну повну схему. Далі встановіть `NP_ENCRYPTION_KEY` із `02-secrets.env` у **Edge Functions → Secrets**, а в **Edge Functions → Deploy a new function → Via Editor** створіть `nova-poshta`, вставте вміст `03-index.ts` у `index.ts` і натисніть Deploy. У деталях функції вимкніть gateway JWT verification: функція сама перевіряє користувацький токен.

Перевірити URL у Dashboard можна до запуску. Планувальник бази не потрібен: перевірка працює лише поки відкрита вкладка Нової пошти.

Для кожного проєкту створюється свій `NP_ENCRYPTION_KEY`; генератор зберігає його локально і не виводить у термінал. Не змінюйте його після збереження API ключа НП: тоді старий шифротекст не розшифрується. Секрет синхронізації cron більше не потрібен.

За останнім уточненням користувача всі параметри підключення зберігаються в новому стовпці `public.settings.novaposhta` типу JSONB, рядок `setting_id=10`. Поля: `schema_version`, `name`, `phone`, `enabled`, `needs_reconnect`, `refresh_minutes`, `last_sync`, `last_error`, `incoming_capability`, `api_key_encrypted`. Ключ зберігається лише як шифротекст AES-GCM; ключ шифрування знаходиться у секретах Edge Function. Колонка «Загальні» та решта наявних налаштувань не змінюються. Введення і видалення ключа — у розділі «Нова пошта → Налаштування Нової пошти», тільки адміністратором. Запис виконує сервер; браузерні ролі не можуть змінювати JSON налаштувань НП. Посилки, їхня історія і зв’язки з актами зберігаються у таблицях `np_*`, щоб підтримувати пошук, права доступу й одночасну роботу пристроїв.

## 2. Серверні секрети

У Supabase Dashboard → Edge Functions → Secrets додайте один запис із `02-secrets.env`:

| Назва | Значення |
|---|---|
| `NP_ENCRYPTION_KEY` | Випадкові 32 байти як 64 шістнадцяткові символи — ключ AES-GCM |
| `ALLOWED_ORIGINS` | За потреби: точні HTTPS-адреси сайту через кому, без шляхів і кінцевого `/` |

Збережіть ключ шифрування в захищеному місці: його заміна без повторного введення API-ключа НП зробить старе зашифроване значення непридатним. Не використовуйте префікс `VITE_` і не додавайте ці секрети в код, чат чи браузерне сховище.

`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` надаються середовищем Supabase Edge Functions. Сам API-ключ НП вводиться пізніше через форму адміністратора; він не є змінною frontend.

## 3. Серверна функція

Dashboard-редактор створює функцію через **Deploy a new function → Via Editor**. Вставте в `index.ts` згенерований `03-index.ts` і натисніть Deploy. Функція сама перевіряє JWT користувача через Supabase Auth, whitelist та сесію працівника.

## 4. Оновлення вручну

Авторизований працівник відкриває розділ і натискає «Оновити зараз», щоб завантажити посилки та перевірити статуси. Автоматичного таймера немає.

Результати перевірок дивіться у журналі синхронізацій:

```sql
select started_at, finished_at, outcome, updated_count
from public.np_sync_runs
order by started_at desc limit 10;
```

Завершення синхронізації перевіряйте в `np_sync_runs`: `success`, `partial` або `error`. Нові перевірки запускаються лише за дією працівника.

## 5. Сайт і підключення акаунта

Опублікуйте frontend звичайним процесом Vercel після встановлення серверної частини. `npm run build:vercel` — локальна збірка, сама по собі нічого не публікує. Для нової копії змініть змінні середовища саме її Vercel-проєкту. Налаштуйте також Google OAuth redirect URL для нового Supabase URL, перенесіть whitelist і потрібні записи працівників/акти у його базу та розгорніть туди функцію й обидві міграції.

Зв’язки, історія, права та описи посилок зберігаються окремо в кожному Supabase-проєкті. Якщо в обох проєктах ввести ключ того самого акаунта Нової пошти, обидва зможуть бачити посилки, які повертає цей акаунт. Щоб бачити різні акаунти перевізника, підключайте в кожному проєкті відповідний окремий ключ.

1. Увійдіть у СТО як Адміністратор і відкрийте іконку НП → «⚙ Налаштування Нової пошти».
2. Підтвердіть пароль поточного працівника СТО. Це додаткова серверна перевірка існуючого працівника, а не пароль Нової пошти.
3. У налаштуваннях Нової пошти, введіть назву, телефон акаунта НП та API-ключ із бізнес-кабінету НП.
4. Натисніть «Перевірити і підключити», потім «Оновити зараз».
5. Додайте контрольну вхідну ТТН та прив’яжіть її до відкритого заказ-наряду. Перевірте маршрут, опис, статус і прогноз за даними НП.

Після першого підключення поле ключа залишається порожнім і показує, що ключ збережений. Назву й телефон можна змінити без повторного введення ключа. Нове значення в полі API-ключа замінює попередній ключ після перевірки. «Призупинити синхронізацію» зберігає ключ; «Відновити синхронізацію» перевіряє збережений ключ і вмикає оновлення знову. Стан форми перечитується після кожної дії.

У картці «Перевірити цю посилку зараз» перечитує статус, маршрут, дати та історію без закриття вікна. Незбережений власний опис залишається у формі. Якщо інший працівник паралельно змінив власні поля, показується повідомлення про конфлікт; його зміни не перезаписуються автоматично.

На кожному пристрої працівник входить у СТО звичним способом і підтверджує свій пароль для розділу НП. Сесія НП прив’язана до Google/Supabase-користувача та працівника, зберігається в `sessionStorage` вкладки і має серверний строк 7 днів. Інші пристрої залишаються авторизованими. Нову вкладку або завершену сесію потрібно підтвердити знову; повторне введення ключа НП не потрібне.

Адміністратор, Приймальник, Запчастист і Складовщик мають початковий доступ. Адміністратор може змінити доступ інших працівників у формі. Додатковому працівнику може знадобитися перезавантажити сторінку для появи іконки. Перемикач у налаштуваннях приховує іконку, але не вимикає серверний розклад.

## 6. Приймання на реальних даних

- Перевірити по одній ТТН: створена, у дорозі, прибула до нас, отримана, вихідна, повернення/відмова.
- Зіставити поля API і коди статусів із офіційним відстеженням. Відсутній прогноз має показувати «Не вказано». Дата створення ТТН не вважається датою фактичного відправлення.
- Перевірити отримання вихідних документів акаунта, пагінацію та доступні можливості вхідного списку.
- Відкрити два пристрої: перевірити спільні зміни, незалежні сесії, конфлікт редагування, персональне прочитання повідомлень.
- Перевірити права всіх потрібних ролей, закриті/заморожені акти, відкликаний доступ та недійсний ключ.
- Підтвердити, що відкриття розділу й очікування не запускають синхронізацію, а «Оновити зараз» створює запис у `np_sync_runs`.

## Локальні перевірки

27.09.2026 виконано перевірку TypeScript, збірку Vercel, перевірку серверної функції Deno. Перша SQL міграція виконувалася у тестовому PostgreSQL/PGlite. Браузерні сценарії виконувалися у headless Edge на контрольних відповідях API без звернення до робочої бази. Перевірки прав, прив’язок, конкурентних змін, статусів, мобільного інтерфейсу та наявні регресійні перевірки актів/меню/завантаження зібрані у 31 успішний тест.

28.09.2026 після додавання керування ключем повторно пройшли збірка Vercel із TypeScript і перевірка Edge Function через Deno. Нову міграцію керування ключем у робочій базі ще не виконано; попередній результат 31 тесту не є перевіркою цієї нової міграції.

Основна команда (додаткові PGlite/Playwright встановлено поза залежностями проєкту):

```powershell
$env:NP_VALIDATION_ROOT = Join-Path $env:TEMP 'sto-np-validation'
node --test tests/nova-poshta.test.cjs tests/nova-poshta-ui.test.cjs tests/login-bundle.test.cjs tests/act-persistence.test.cjs tests/menu-icons.test.cjs
```

Тестовий транспорт не доводить працездатність реального API НП або налаштувань робочого Supabase. Ці перевірки залишаються до активації.

## Зупинення

«Призупинити синхронізацію» у формі адміністратора зупиняє перевірки зі збереженням історії. Закриття розділу також зупиняє його таймер; інших фонових запусків немає.

Кнопка відключення зберігає зашифрований ключ; заміна виконується через повторне підключення. Окрема кнопка «Видалити збережений API-ключ» після підтвердження очищує його зі сховища Supabase та зупиняє синхронізацію. Посилки і прив’язки залишаються. Це не відкликає ключ на стороні НП: за потреби відкликайте його в бізнес-кабінеті. Якщо API повідомить про недійсний ключ, підключення переходить у стан «Потрібно перепідключити», а регулярні запити призупиняються.
