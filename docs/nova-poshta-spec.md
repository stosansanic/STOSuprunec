# ТЗ: інтеграція Нової пошти із системою СТО

Версія 1.1. Дата: 27.09.2026. Статус: основний модуль реалізовано локально; серверна активація та приймання на реальному API попереду.

Інструкція запуску й фактичні обмеження: [nova-poshta-setup.md](nova-poshta-setup.md). Це ТЗ залишається цільовим описом: успішні локальні перевірки не означають виконання всіх критеріїв приймання на робочому акаунті.

## 1. Мета та межі першої версії

Єдиний розділ для вхідних і вихідних посилок СТО: маршрут, опис, очікуване прибуття, поточний статус та зв’язок із заказ-нарядами. Відкривається через наявну круглу іконку Нової пошти в головному меню.

Перша версія: підключення акаунта, імпорт доступних через API відправлень, додавання ТТН, відстеження, прив’язка до актів, фільтри та внутрішні сповіщення. Створення платних відправлень, виклик кур’єра, переадресування, оформлення повернення й оплата — окремий наступний етап. Повернення, уже оформлене через Нову пошту, потрібно відображати й у першій версії.

## 2. Підключення та вхід

1. Адміністратор створює API-ключ у бізнес-кабінеті Нової пошти.
2. У нашій програмі відкриває «Нова пошта → Підключення» та вводить назву підключення, ключ, контактний телефон СТО й свої міста/відділення. Дані акаунта, які повертає API, підставляються після перевірки.
3. Сервер перевіряє ключ без створення відправлень. Екран показує результат і доступні можливості: відстеження, імпорт вихідних, імпорт вхідних.
4. Після збереження інші дозволені працівники працюють через власний чинний вхід у систему СТО. Окремий логін у Нову пошту для кожного працівника не потрібен.
5. Пароль і SMS-коди Нової пошти наша програма не запитує. Для заміни ключа є окрема дія адміністратора. Сам ключ після збереження не повертається браузеру.

Остаточне уточнення користувача 28.09.2026: параметри підключення НП зберігати в новому JSONB-стовпці `settings.novaposhta`, рядок `setting_id=10`. Ключ — у полі `api_key_encrypted`, виключно зашифрований AES-GCM. Ключ шифрування — у секретах серверної функції. Введення та заміна ключа — в налаштуваннях самої Нової пошти. Не змінювати стовпець «Загальні». Сервер перевіряє адміністратора перед записом; браузерні ролі не можуть змінювати конфігурацію НП напряму. Посилки, історія та зв’язки з актами зберігаються у відповідних таблицях модуля. Відкритий ключ не записується в localStorage, VITE-змінні, логи або відповіді API.

Для першої версії — одне активне підключення СТО, структура даних передбачає додавання інших. Відключення припиняє синхронізацію, але зберігає історію й зв’язки з актами.

Одне підключення НП спільне для всіх уповноважених працівників СТО, а не прив’язане до пристрою адміністратора. Адміністратор, приймальники, запчастисти, складовщики та інші працівники з наданим доступом можуть одночасно працювати зі своїх телефонів, планшетів і комп’ютерів. Кожен входить у власний обліковий запис СТО. Один працівник також може мати активні сесії на кількох своїх пристроях; новий вхід не повинен примусово завершувати попередній. Під час реалізації перевірити сумісність чинного механізму сесій із цією вимогою.

Всі пристрої читають спільні посилки та прив’язки із Supabase. Зміни статусів і зв’язків надходять у відкриті екрани через Realtime, а після відновлення з’єднання дані перечитуються. Стан прочитання сповіщень зберігати для кожного працівника й синхронізувати між його пристроями. Одночасне редагування тієї самої прив’язки/примітки має виявляти конфлікт версій, щоб один працівник непомітно не затер зміни іншого.

## 3. Джерела даних та обмеження

Нова пошта є джерелом фактичних статусів перевезення, доступних даних маршруту та прогнозу доставки. Supabase зберігає останні отримані значення, історію змін, власний опис деталей, прив’язки до актів, відповідальних і налаштування.

Автоматичний імпорт вхідних і вихідних посилок реалізовується в межах офіційного API та прав підключеного акаунта. Перед основною розробкою обов’язково перевірити на реальному акаунті, чи доступний повний список вхідних, чи потрібний телефон і які поля повертаються. Відстеження за відомою ТТН та пошук усіх посилок акаунта — різні можливості.

Якщо автоматичний список вхідних недоступний, явно показувати це у підключенні. Доступні альтернативи: вставити одну/кілька ТТН або додати ТТН в акті. Не називати вручну внесений список «усіма посилками акаунта». Повна автоматична видимість вхідних залишається окремою непідтвердженою вимогою до перевірки API.

Опис Нової пошти може бути загальним або відсутнім. Тому окремо зберігати «Опис НП» і редагований «Для СТО», наприклад «Генератор BMW, ремонт». Синхронізація не перезаписує власний опис.

Відсутні дані показувати як «Не вказано», прогноз — як «Очікується …». Не вигадувати час прибуття або поточне місто. Місто відправника та місто останнього сканування, якщо воно доступне, відображати окремо.

## 4. Напрямок та статуси

Напрямок — окреме поле: «До нас» або «Від нас». Визначати за підтвердженою належністю відправника/отримувача акаунту СТО; одного збігу міста недостатньо. Якщо визначити неможливо — «Уточнити напрямок» із ручним вибором та журналом зміни.

| Стан | До нас | Від нас |
|---|---|---|
| Створена ТТН | Постачальник створив накладну; передачу перевізнику ще не підтверджено | Накладна створена; передачу перевізнику ще не підтверджено |
| У дорозі | Посилка рухається до СТО | Посилка відправлена від СТО до отримувача |
| Прибула | «Потрібно забрати» або відповідний стан адресної доставки | «Очікує отримувача» або відповідний стан адресної доставки |
| Отримана | «Ми отримали» | «Отримувач забрав» |
| Потребує уваги | Відмова, повернення, переадресування, проблема доставки | Відмова, повернення, переадресування, проблема доставки |

Окремо підтримати скасовану/видалену накладну, ТТН, яку не знайдено, та невідомий новий статус. Зберігати оригінальний код і текст НП поряд із нашою категорією. Відповідність кодів категоріям затвердити після перевірки актуальної документації та контрольних відповідей API.

Завершене повернення не вважати успішним отриманням початковим адресатом. За наявності нової ТТН зв’язувати її з початковою як окреме перевезення.

Статус «Отримана» не оприбутковує деталі на склад і не закриває акт автоматично. За потреби окремо дозволити внутрішню позначку «Передано на склад» із відповідальним і датою.

## 5. Головний екран

На комп’ютері — велике вікно приблизно 90% ширини; на планшеті й телефоні — на доступний екран. Прокручується вміст, заголовок і основні фільтри залишаються доступними.

Угорі: назва підключення, час останнього успішного оновлення, «Оновити», «Додати ТТН»; адміністратору також «Підключення».

Вкладки напрямку: «До нас», «Від нас», «Усі». Швидкі фільтри з лічильниками: «Потрібно забрати», «У дорозі», «Очікуємо сьогодні», «Без заказ-наряду», «Потребує уваги», «Отримані». Типовий початковий перегляд — активні вхідні; посилки, які потрібно забрати, стоять першими.

Таблиця: ТТН; напрямок; маршрут «місто → місто»; опис; статус; очікувана дата; відділення/адреса; заказ-наряди; відповідальний. Другорядні дати й детальна історія — у картці посилки. Довгі назви переносяться. На телефоні рядки перетворюються на картки.

Клік на ТТН відкриває деталі: повний доступний маршрут, оригінальний статус, історію зафіксованих змін, дати, описи, зв’язки з актами та дію переходу до офіційного відстеження.

Кольори: створена — сірий; у дорозі — блакитний; потрібно забрати — теплий жовтий; отримана — зелений; проблема — світло-червоний. Кожен колір супроводжується текстом.

На іконці меню — кількість вхідних посилок, готових до отримання. Сповіщення про нове прибуття створюється один раз на подію. Уже переглянуті сповіщення повторно не з’являються після оновлення сторінки.

## 6. Прив’язка до заказ-нарядів

В акті додати блок «Нова пошта» з дією «Додати посилку». Поле дозволяє вставити ТТН або вибрати відому посилку з пошукового випадаючого списку. У списку показувати ТТН, напрямок, опис, маршрут і статус; список відкривається під полем.

Якщо ТТН нова, отримати її дані через сервер, показати результат і після підтвердження зберегти посилку та зв’язок. При недоступності НП дозволити зберегти її як «Очікує перевірки», без вигаданого статусу. Неправильний формат позначити біля поля.

Один акт може мати кілька посилок. Одна посилка може містити деталі для кількох актів. Тому використовувати окрему таблицю зв’язків, а не один номер ТТН у JSON акта.

Для кожного зв’язку: акт, посилка, призначення («Деталі до нас», «Відправлення на ремонт», «Повернення постачальнику», «Інше»), опис деталей/примітка. За наявності стабільних ID рядків акта — необов’язковий зв’язок із конкретною позицією; не використовувати індекс рядка як постійний ідентифікатор.

У розділі НП показувати номер акта, авто/держномер і перехід до доступного користувачу акта. В акті показувати всі пов’язані ТТН та їхні актуальні збережені статуси. Для закритих або заморожених актів дотримуватися чинних правил редагування.

При додаванні вже наявної ТТН використовувати існуючу посилку. Якщо вона пов’язана з іншими актами, показати це й дозволити додаткову прив’язку без видалення попередніх. «Відв’язати» прибирає тільки зв’язок, не видаляє посилку в НП.

## 7. Фільтри та сортування

- Напрямок, одна/кілька категорій статусу, місто відправлення/отримання, відділення, відповідальний.
- Період із явним вибором типу дати: створення, відправлення, очікуваного прибуття, фактичного прибуття або отримання.
- Швидкі періоди: сьогодні, завтра, останні 7/30 днів; власний діапазон.
- Пошук за ТТН, описом, номером акта, авто/держномером; за клієнтом — лише в межах доступу до актів.
- Зв’язок: усі / без акта / з актом / конкретний акт. Помилка оновлення — окремий фільтр від проблеми доставки.
- Сортування: спочатку потрібно забрати, найближче очікуване прибуття, остання зміна статусу, дата створення.

Фільтри комбінуються; є «Скинути». Вибір користувача зберігається. Дати показувати в Europe/Kyiv; невідомі дати не підміняти датою додавання до нашої системи.

## 8. Сервер та зберігання

Схема роботи: браузер → серверна функція Supabase → API Нової пошти → нормалізація й збереження → оновлення інтерфейсу.

Запропоновані таблиці:

| Таблиця | Призначення |
|---|---|
| nova_poshta_connections | Назва підключення, належність до СТО, контакти, доступні можливості, стан синхронізації; без відкритого API-ключа |
| settings.novaposhta | Параметри підключення та шифротекст ключа; запис тільки через сервер |
| shipments | Унікальна ТТН у межах СТО/перевізника, напрямок, маршрут, оригінальний і нормалізований статуси, описи, дати, останнє успішне оновлення |
| shipment_act_links | Зв’язки з acts.act_id, призначення та примітки; унікальність пари посилка–акт |
| shipment_events | Зафіксовані зміни статусу, час події перевізника за наявності, окремо час нашого спостереження |
| shipment_notifications | Події для працівників і стан прочитання |
| shipment_sync_runs | Час запуску, результат, кількість оновлень і безпечний опис помилок |

Зберігати лише потрібні поля відповіді API. Історія наших спостережень не видається за повну історію перевезення до першого імпорту. Індекси потрібні для ТТН, статусу/напрямку, дат і act_id; список має серверну пагінацію.

Усі запити перевіряють доступ до конкретного СТО, підключення й акта. RLS захищає таблиці, клієнт не може записувати статуси перевізника або читати секрети. Журналювати зміну ключа, прив’язок, внутрішнього опису й відповідального без секретів.

## 9. Оновлення та помилки

Перевірка Нової пошти запускається вручну кнопкою «Оновити зараз». Таймер і серверний планувальник не використовуються. Блокування підключення захищає від одночасної синхронізації на кількох пристроях.

При відкритті відразу показувати спільні збережені дані та час останнього успішного оновлення. Саме відкриття вкладки не запускає додатковий запит до НП. Кнопка «Оновити зараз» дозволяє уповноваженому працівнику перевірити дані до наступного планового циклу. Повторні ручні запити обмежуються на сервері; якщо оновлення вже триває, інші пристрої приєднуються до його результату. Ручний і плановий запуск не виконуються паралельно для одного підключення.

Завершені посилки прибрати з частого опитування після контрольного оновлення; ручне оновлення лишається доступним. Врахувати пагінацію імпорту, повторні запуски, дублікати, блокування паралельних синхронізацій і повтори з поступовою затримкою при тимчасових помилках.

Помилка API не очищає список і не змінює статус доставки. Показувати «Не вдалося оновити; дані станом на …». Недійсний ключ переводить підключення в стан «Потрібно перепідключити» та повідомляє адміністратора. Помилка одного підключення не блокує інші функції програми.

## 10. Права

За замовчуванням перегляд і робочі дії — для Адміністратора, Приймальника, Запчастиста, Складовщика, з урахуванням наявних прав на акти. Адміністратор може надати доступ іншим ролям/працівникам; без такого дозволу доступ закритий. Кількість одночасних працівників і пристроїв не обмежується одним користувачем або одним пристроєм. Доступ до розділу НП не розширює наявні права на чужі або закриті акти.

Підключення, заміна/видалення ключа й керування правами — лише Адміністратор. Існуючий перемикач керує видимістю іконки; серверні права перевіряються окремо. При прихованій іконці фонова синхронізація продовжується, доки адміністратор не відключить підключення.

## 11. Порядок реалізації та приймання

Етап 1: на наданому через захищений інтерфейс ключі перевірити можливості акаунта, доступність вхідних/вихідних, необхідність телефону, поля, статуси, пагінацію та ліміти. Зафіксувати підтверджений контракт API. Ключ не надсилати в чат.

Етап 2: міграції таблиць, серверна авторизація, захищене зберігання ключа, перевірка підключення, додавання ТТН і синхронізація.

Етап 3: головний список, картка посилки, фільтри, адаптивний інтерфейс, двостороння прив’язка до актів.

Етап 4: фонові оновлення, лічильник, сповіщення, обробка помилок та перевірка на контрольних посилках.

Критерії приймання:

1. Вхідна посилка показує місто відправлення, доступний опис, прогноз і перехід «У дорозі → Потрібно забрати → Ми отримали».
2. Вихідна показує пункт призначення та перехід «У дорозі → Очікує отримувача → Отримувач забрав».
3. Створення ТТН без передачі посилки не відображається як рух вантажу.
4. Підтверджені API можливості імпорту працюють; обмеження вхідного списку чітко видно користувачу.
5. Прив’язка, створена в акті, одразу видима в списку НП і навпаки; кілька актів/посилок підтримуються без дублікатів.
6. Період фільтрує саме обраний тип дати. Довгі назви й мобільний список читабельні.
7. API-ключ відсутній у клієнтському коді, localStorage, відповідях перегляду та логах; заборонені серверні дії відхиляються.
8. Відмова, повернення, невідома ТТН, відсутній прогноз, помилка API та відкликаний ключ мають коректні окремі стани.
9. Повторні оновлення не створюють дублікати посилок, зв’язків або сповіщень і не стирають внутрішні описи.
10. Збірка й наявні перевірки запуску проходять; таблиця актів, календар, склад та розпізнавання накладних продовжують працювати.
11. Перевірка нових посилок і статусів запускається вручну. Відкриття розділу не запускає запити до НП.
12. Адміністратор, приймальник, запчастист і складовщик одночасно бачать спільні посилки та зміни в межах своїх прав. Додатковий дозволений працівник також має доступ; працівник без дозволу — ні.
13. Вхід працівника з другого пристрою не завершує його першу сесію. Після відновлення мережі пристрій отримує актуальні дані; конкурентні зміни не втрачаються непомітно.
14. «Оновити зараз» оновлює дані для всіх пристроїв; одночасні натискання не створюють паралельних циклів, дублікатів або повторних сповіщень.
