# Перевірка нових функцій 2, 3, 5, 6

## Де вони доступні

- **Сервісна книга → «Стани рекомендацій» → вкладка «🔧 Дефектування»**: вузол, компонент, вимірювання до/після, допуск, дефект, потрібна операція, стан і HTTPS-посилання на наявне фото. Допуски вводяться працівником, програма їх не вигадує. За побажанням користувача блок запуску картки з самого акта прибрано.
- **Сервісна книга → «Стани рекомендацій»**: запропоновано / погоджено / виконано / відхилено. Старий текст рекомендацій не замінюється.
- **Масове введення складу → «📷 Накладна з фото/PDF»**: розпізнати, перевірити поля та всі рядки, обрати стан отримання деталей, підтвердити звірку, перенести в таблицю. Лише звичайна кнопка «Записати» записує позиції на склад.
- **Атлас → «❗ Увага» після «📊 Дашборд»**: огляд записів, що потребують уваги, з фільтром категорій та кнопкою оновлення. Це перевірка за правилами, а не висновки мовної моделі. Акти, залишки й зарплати не змінюються.

## Зберігання й обмеження

- Без нових таблиць, колонок, RPC та міграцій. Картки/статуси містяться в допоміжному розділі `acts.data.__workshop_v1`. Позиції накладної — у наявній таблиці `sclad` через звичайний механізм запису.
- Для нових функцій не використовується постійне зберігання у браузері. Незбережена форма живе лише у відкритому вікні; для запису картки потрібне з'єднання. Закриття зміненої форми потребує підтвердження.
- Збереження перевіряє ревізію акта та вихідну версію редагованого запису. Конфлікт редагування одного запису не перезаписується мовчки.
- Дефектування закритих/заморожених актів доступне лише для читання. Окремі статуси рекомендацій можна оновлювати без зміни робіт, деталей і нарахувань.
- Розпізнавання передає вибраний файл наявному провайдеру Gemini/OpenRouter після явного натискання користувача. PDF підтримано через Gemini. Потрібні налаштований ключ і доступна модель. Результат ШІ завжди потребує ручної звірки; поточний імпорт підтримує гривню.
- Перевірка повторного імпорту використовує постачальника/номер та позначки рядків накладної. **Без унікального обмеження на рівні БД це не гарантія від одночасного імпорту тієї самої накладної з двох пристроїв.** Не імпортуйте одну накладну паралельно. При неоднозначній відповіді після запису спочатку перевірте склад.
- Права використовують чинні перевірки програми; нових правил RLS не додано. Огляд планування для працівника показує створені ним записи, для адміністратора — усі доступні на сьогодні/завтра. Огляд не перевіряє локальні черги інших пристроїв.

## Автоматична та ізольована перевірка

```powershell
npm run check
npm run build:vercel
node --test tests/*.test.cjs
```

`workshop-workflows.test.cjs` перевіряє конфлікти, права, відкриті/закриті/заморожені акти, збереження 55 робіт і деталей, відмову без інтернету, 75 рядків накладної, дублікати, помилки БД, точний ID нового складського запису та ізоляцію запиту розпізнавання. Запити до БД/ШІ замінені тестовими реалізаціями.

Для ручного огляду інтерфейсу без робочої бази:

```powershell
node tests/workshop-preview.cjs
```

Відкрити `http://127.0.0.1:5201/` (ПК) або `/phone` (вузький екран). Усі дані вигадані й зберігаються лише в пам'яті стенда. Реальний провайдер OCR цим стендом не перевіряється.

Перед робочим використанням після публікації: створити тестову картку, перевідкрити її з іншого авторизованого пристрою, перевірити права слюсаря/приймальника й розпізнати тестову накладну на налаштованому провайдері. Публікація на Vercel не є частиною локальної збірки.
